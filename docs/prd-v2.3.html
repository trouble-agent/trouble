01 · The one-liner, upgraded

Errors get resolved — not lost, not surprised-by, not waiting for a human to read a log.

trouble is an open-source Linux daemon where your applications — local or remote, any language — report their errors (a Sentry-compatible endpoint every major SDK already speaks), where the kernel and services raise their own alarms (PSI, units, logs, disk, leaks), and where every finding works a ladder: record → scripted playbook → research (Off-by-One pre-solve) → budgeted AI agent → outlets — issues in your tracker, a board task via direct write, and for confirmed code bugs, hot-fix mode that kicks a worktree foreman immediately, verified and promoted before it's called done. All of it visible in trouble's own dashboard, deduped end-to-end by one signature system.

  • No more silent log files: the whole point is that an exception in a service — on this host or another — becomes a grouped, tracked, worked item with an audit trail, whether or not any human ever opens a terminal.
  • Language-agnostic by construction: Sentry SDKs cover 100+ languages/frameworks with zero code changes; a plain-JSON endpoint covers everything else (one curl from any runtime, cron job, or script); pluggable collector parsers cover legacy apps that only write logs. Nothing is excluded by language choice.
  • Managed hands, researched fixes: the agent never has a shell — only typed tool calls (config parsers, service controls, bounded patches). And before the agent even runs, findings can forward to Off-by-One for pre-solve research, so the agent starts from a brief, not a blank page.

04b · Sentinel — embedded error tracking, local + remote, any language

A Sentry-class service inside the daemon — the network edge for every error your code throws

Sentinel is trouble's code plane: an embedded error-tracking service. Applications report exceptions to it; it fingerprints, groups, counts, and tracks them across releases; and its groups are first-class citizens of the same ladder as a full disk. Local services report over loopback; remote services report over your LAN/Tailscale — same DSN auth (project IDs + public keys), same quotas. A service on another box whose errors used to die in a journal nobody reads now lands in the same groups, dashboard, issues, and hot-fix pipeline as everything else.

Grouping, releases, quotas — and resolution, the point of it all

Fingerprint = group (SDK fingerprints honored; stack canonicalization masks line numbers/addresses/PIDs). Groups carry counts, first/last seen, release + environment tags. Release tracking gives the money queries — new in v0.4.2 = regression → board task auto-filed; flat after the rollback = verified fix → group closes. Quotas per project with 429 + Retry-After keep a runaway app from flooding the daemon (it floods only itself; client sampling respected). Retention compacts quiet groups; the ledger keeps the permanent record. And because groups feed the ladder (§05), a grouped error doesn't just sit in a list — it gets researched, fixed, verified, and closed. That's the difference between Sentry and trouble: Sentry tells you what broke; trouble's job is that it doesn't stay broken.

# anything:

# legacy apps:

04c · The dashboard — trouble's own UI (NEW)

Every group, incident, and fix — visible without opening a terminal

Promoted from "deferred" per directive: trouble serves its own dashboard from the same binary — Go html/template + htmx-style progressive enhancement over embedded static assets, dark theme, zero external stack (no Node build, no SPA framework, no database beyond the ledger). It's the read-mostly face of the ledger; everything shown is already recorded, and the few actions it offers (ack, quiet-close, trigger rule, approve promotion) go through the same authorization as the CLI.

Incidents — live feed: trigger, rung reached, actions, verification status; filter by rule/severity/source; incident detail = the full evidence bundle + tool-call audit trail.
Sentinel — error groups ranked by rate/trend/count; release diff view (new-in / fixed-in); per-project and per-environment breakdowns; the regression queue.
Issues & flow — issue desk state across drivers (github/duckbrain), board tasks filed, hot-fix timelines: filed → foreman picked up → patch → verify window → promoted, with links to the PR/worktree.
System — breaker states, rule health (last fire, suppressed counts), agent budget burn, quota usage, host vitals (PSI mini-graphs). Research lane view: what Off-by-One was asked, what it returned.

Boundaries: dashboard auth = token (same store as the API) or loopback+unix-socket; read-only by default, write actions permission-gated; served on its own port (:8644) so ingestion (:8643) and admin never share an attack surface; works fine over Tailscale for remote nodes. Mobile-friendly because the maintainer reads dashboards on a phone.

05 · The ladder — now with a research rung
①
Record — evidence bundle to the ledger before anything (sensor snapshot and/or sentinel group, top-procs, journal tail, unit states, config versions).
②
Playbook — deterministic reflex in tool calls: service.reload, config.set, drain.pool. Zero tokens, sub-2s. Known problem → known fix.
②½
Research — NEW, per directive: "part of the research before the agent." Unknown-shape findings forward to Off-by-One (the pre-solve lab — idle GPU time turned into pre-solved work) with the fingerprint, stack, release info, and repro context. Off-by-One researches while the incident cools through its stabilization window; the returned brief (root-cause hypotheses, similar-solved cases, proposed patch sketch) is what the agent run starts from — the agent diagnoses from research, not from zero. Pluggable [research] drivers (off-by-one first; none/webhook for OSS users); research is async and never blocks ② or escalation. If research alone yields a confident fix, the agent run can be skipped entirely.
③
Agent — budgeted AI run (25k/8k tokens, 120s, one at a time, two-strikes suspension), now research-informed. Only hands: registry tool calls. Output JSON: {diagnosis, tool_calls[], issue_draft?, confidence}. propose/execute per rule.
④
Outlets — ⑤ escalate (telegram/signal/webhook; always on breakers/failures/review items) · ⑥ issue desk (github/duckbrain; sig-deduped; sentinel groups land here) · ⑦ flow control (direct board write + hot-fix, §08).
06 · Tool registry + the dedup core

Tool registry — the agent's only hands (unchanged contract)

Typed capabilities with JSON schemas, daemon-implemented: config.get/set/unset/list (TOML/YAML/JSON/env/ini parsers, formatting-preserving, schema-validated) · service.reload/restart/stop/start/status (D-Bus) · file.read/patch (allowlists, backups, rollback records) · proc.top/connections/signal (signal allowlist) · flow.file_issue/create_task/comment · custom: script tools (v1.1). Every call: authorize → validate → dry-run → apply → verify → audit; failed verify rolls back and escalates.

Ansible-grade module semantics — the "scalable ability without risk" answer

Borrowed deliberately from Ansible, the 15-year proven pattern for machine-managed change — its three load-bearing ideas become registry law:

  • Idempotency: every module defines desired-state semantics — running twice yields "ok", not a second change. The agent can retry safely; flakes can't compound. Conformance-tested per module.
  • check_mode everywhere: dry-run isn't a convention, it's a module contract — every tool computes and returns the diff it would apply without applying. (v2.0's dry-run stage made mandatory per-module.)
  • Plays = declarative remedies: multi-step fixes are DATA, not improvised orchestration — ordered tool-call sequences with when: conditionals, retries, and per-task changed/ok/fail results. The agent drafts a play; the runner executes it through the same 6-stage contract. The agent never orchestrates live — it writes the script of what should happen, and boring machinery performs it.

This is how ability scales without risk growing: new capability = one new schema'd, conformance-tested module (descriptor + Go impl + tests), reviewed like code — never more agent freedom. A plays/ library ships curated remedies; the agent's drafted plays land there as candidates (same promotion loop as skills, §06c). Ansible interop note: the community's 3,000+ modules are Python — a v1.1 bridge can exec selected stable modules in a pinned venv as custom: tools (declared schema, audited) instead of reimplementing the world.

The dedup core — one signature space, everything deduped (NEW named subsystem)

Dedup isn't a feature of the issue desk anymore; it's the canonical signature core every plane feeds and every consumer reads:

  • One sig format: {source}:{canonical-hash} — sensors hash (rule + normalized condition + affected unit), sentinel hashes fingerprints, collector parsers hash canonicalized stacks. Same normalization rules everywhere.
  • Cross-plane convergence: sensor incident + sentinel group within the window on the same unit → ONE incident, both bundles attached (the crash-loop + error-stream merge).
  • Every consumer dedupes on it: issues (recurring sig = comment + counter on the existing issue, never a new one), board rows (sig already has an open row → comment/cross-ref, never a duplicate task), escalations (sig in active cooldown → suppressed), dashboard (sig is the join key), hot-fix verification (the sig must stay quiet for the window).
  • Ledger cross-links: one sig → {incidents[], groups[], issues[], tasks[], research_briefs[]} — the full life of a bug in one query, which is also the dashboard's incident-story view.
06c · The skill loop — it learns, like hermes (NEW)

Incidents become skills. Review ships them down. Every host gets smarter.

v1.0's promotion loop (agent-fix → playbook candidate) generalizes into a skill system with the same shape as hermes skills — procedural memory that improves with every incident:

# ~/.trouble/skills/payment-worker-queue-wedge.toml
name        = "payment-worker-queue-wedge"
version     = 3
sigs        = ["sentinel:9f2c…", "journal:payment-worker:restart-loop"]   # which signatures it handles
[play]                                           # a declarative play (§06) — the remedy
- tool = "proc.connections"; args = { unit = "payment-worker" }
- tool = "service.reload";   args = { unit = "payment-worker" }; when = "connections > 400"
- tool = "config.set";       args = { path = "/etc/payment/worker.toml", key = "pool.max",
                                      value = 250, validate_only = false }
[guards]
verify_window = "10m"                            # sig must stay quiet after
max_runs     = "3/day"
escalate_on  = "verify_fail"
[provenance]                                     # what taught it — full audit chain
incidents = ["inc_8812", "inc_8907"]             research = ["ob1_brief_2214"]
[stats]                                          # live, updated by the daemon
applied = 4   success = 4   last_used = "2026-09-03"
  • The loop: incident → ladder ③ agent fix → captured as candidate skill (provenance-linked to the incident + research brief) → verified in the window → reviewed (human default) → promoted → next occurrence anywhere runs as ② at zero tokens. Playbook thickens, agent runs get rarer — the system measurably heals itself over time, and the ledger proves it.
  • Distribution — up and down (the new part): skills live in a git skills repo (the natural OSS answer: review = PR, audit = history, distribution = pull). trouble pushes candidates up as PRs and pulls reviewed skills down on interval/webhook. Cross-host learning: host A's incident teaches the repo; hosts B and C pull the skill; the next occurrence on any host is already a reflex. Pluggable remotes: local-only (default, no hub needed) · git repo · DuckBrain namespace (fleet) · a hub service (later).
  • Offloaded deployment shape — on-host or hosted brains: trouble runs full on capable hosts; on weak ones (N100, Raspberry Pi, crowded VPS) it runs in light mode: a ~5MB collector/executor — sensors + sentinel ingestion + skill execution + incident forwarding UP to a hub host running the full daemon (ledger, dashboard, research, agent). Fixes and updated skills come DOWN. The machine stays light under stress; the brains live where resources are; learning still lands on the box that needs it.

08 · Flow control — direct board write + instant worktree foreman

Hot-fix mode: the foreman is working while the incident is still warm

Flow control writes findings into the work system. Two drivers, both first-class per directive: direct board write (board-jsonl — trouble appends the row itself: fastest, works even when the router is down) and task-router (the standing doctrine for normal filing). Hot-fix-grade incidents take the direct lane and go further — they kick off a worktree foreman immediately:

[flow]
driver = "board-jsonl"                      # direct write (or "task-router")
review_mode = "auto"                        # auto | review | never (+ overrides)
[flow.hotfix]
enabled = false                             # host master gate
allowed_repos = ["/srv/src/payment-api"]    # repos a hotfix may touch
unit_repo_map  = { "payment-worker" = "/srv/src/payment-api" }
foreman_spawn = "router_spawn"              # fleet spawn machinery
verify_window = "10m"
promote = "human"                           # human | auto-after-verify

The timing-authority note — honest amendment v1.0 fenced "trouble never spawns workers; the scheduler owns all timing." This directive amends it explicitly: hot-fix lane is the one granted exception — when a confirmed code bug meets enabled + allowed_repos + severity, trouble spawns the worktree foreman now, because fix latency is the point. The fence holds everywhere else (research forwards, normal filing, chores never spawn anything). The exception is config-gated, off by default, and every use is ledger-audited — an auditable bypass, not a second scheduler.

11 · Guardrails, acceptance criteria, open questions

Guardrails

  • Do-not-touch enforced at the registry layer (protected paths/units refused before validation). Every tool call: authorize → validate → dry-run → apply → verify → audit; failed verify rolls back + escalates.
  • Dedup + issue caps + quiet-close + ingestion quotas: neither a chatty app nor a flappy rule can spray anything — groups, issues, rows, or pages.
  • Hot-fix: master gate off, allowed_repos empty, worktree-isolated, verify-window gated, promotion human — every default safe; every spawn audited.
  • Research lane is async and best-effort: Off-by-One down or slow never blocks ②, ③, or escalation — it only enriches.
  • Storm mode, OOM immunity (OOMScoreAdjust -500, MemoryMax=64MB), rename-over upgrades — carried unchanged. Dashboard is token-authed, read-mostly, separate port from ingestion.

Acceptance criteria (v1 AC-1..9 + v2.1 AC-10..17 carry; new below)

  1. AC-18 Remote + language matrix: services on two different hosts — one Go (Sentry SDK), one bash (curl JSON) — report the same bug class; both land in their project groups on the trouble host over Tailscale; dashboard shows both; quotas hold when one floods.
  2. AC-19 Dashboard: from a phone browser, token-authed: live incident appears within 2s of trigger; sentinel release-diff view shows the regression; hot-fix timeline shows filed→foreman→verify→promote with PR link; all read-only actions work without write grants.
  3. AC-20 Research lane: unknown fingerprint + off-by-one enabled → brief forwarded, agent run consumes the returned brief (prompt shows it), incident ledger links brief↔agent↔fix; off-by-one forced-unreachable → ladder proceeds unchanged, gap noted in ledger.
  4. AC-21 Hot-fix immediacy: enabled host + scripted bad line in an allowed repo → direct board row + worktree foreman spawned within 60s of trigger; patch lands in the worktree only (main checkout untouched); verify window passes → promotion prompt; recurrence → rollback + reopen.
  5. AC-22 Dedup totality: same underlying bug detected via sensor AND sentinel AND collector paths → one incident, one group, one issue, one board row (comments on recurrence), one dashboard story; zero duplicates anywhere.
  6. AC-23 Module conformance: every shipped module passes the conformance suite — idempotency (double-apply = ok/ok, one change), check_mode returns the true diff without applying, schema violations rejected at validate; a deliberately non-idempotent test module fails CI.
  7. AC-24 Skill distribution: host A's agent fix → candidate PR → review-merged → hosts B and C pull → synthetic recurrence on B runs as ② at zero tokens with provenance intact (inc_8812 visible in B's ledger).
  8. AC-25 Light-mode offload: N100-class host runs light agent → incident forwarded up to hub → hub researches/fixes → updated skill pulls down → next local occurrence handled locally, offline-tolerant (queued forward).
  9. AC-26 Zero-human loop: autonomy=full host + scripted service bug: detection → research → play → hot-fix foreman → PR merged by policy → verify window → promote → skill candidate auto-accepted (threshold met) — ledger + dashboard show every step, zero human actions; kill-switch stops the loop within one stage.
  10. AC-27 Proxy relay: app → proxy (customer edge) → hub: grouping, quotas, and DSN auth intact through the relay; proxy offline → local spool → flush on reconnect, no loss.

Open questions (one-liners, or defaults stand)

  1. Off-by-One contract: forward shape = fingerprint + stack + release + repro context; return = structured brief (hypotheses, similar cases, patch sketch). Need to pin the lab's actual API (off-by-one-api skill) — integration spike S-OB1, small.
  2. Dashboard stack: Go templates + htmx-style enhancement (my default — zero build chain, ages well) vs a tiny Preact SPA. Default: templates.
  3. Remote ingestion auth: DSN public keys over LAN/Tailscale (Sentry model, my default) vs requiring per-project tokens on top for untrusted networks. Default: DSN model + bind guidance; tokens as an option.
  4. Repo name: trouble (collision check pending; alternates trouble-daemon, gettrouble). Public from first commit recommended.
12 · The ecosystem — the coding-hermes stack, proxies, and the zero-human loop

Part of a deployable ecosystem — and the pitch is software that fixes itself

trouble is not a lone daemon; it's a citizen of the coding-hermes stack — the open, deployable system this fleet already runs: the scheduler (timing authority), task-router, the task board + boardctl, DuckBrain (memory/backends), the usage observatory, DAGger (pipeline runtime), Mallard (data services). Every piece is config-driven and open-source by the same rules, so a stranger can deploy the whole platform or any slice of it: trouble integrates natively (board writes, task-router dispatch, worktree foremen, DuckBrain issue backend) and degrades gracefully alone (board-jsonl, webhook everything, resolver=none).

The ecosystem story
Build and deploy software for services you host → your code reports errors via sentinel (SDK/JSON/collector) → through a proxy if the software runs at your users' edge → the full machinery groups, researches, fixes, verifies, promotes, and learns — automatically. trouble is the "it gets fixed" half of the platform; the scheduler/board/foremen are the "work happens" half; DuckBrain/observatory/mallard are the "state and data" half.
Sentinel proxy — reports from anywhere
A tiny forwarder binary (trouble proxy, one flag): apps report to the nearest proxy (same Sentry-compatible surface, same DSNs), the proxy relays to the hub trouble with spool-and-flush offline tolerance and per-project quotas. Autonomy modes — the zero-human loop is a deployment posture
autonomy = shadow | assisted | full. shadow (default): everything runs — detection, research, plays, even hot-fix foremen — but PRs stay unmerged and promotions wait; you watch the dashboard and build trust. assisted: auto where you've approved (per rule). full: zero humans in any loop — merge-by-policy after verify, skill candidates auto-accepted past a success threshold, issues filed and closed automatically. The safety spine is what makes full defensible: idempotent conformance-tested modules, plays-as-data (never improvised orchestration), worktree isolation, verify windows, dedup caps, storm breakers, and the append-only ledger auditing every step. Full mode is recommended only after a shadow period with green stats — the system earns autonomy, measurably.
Kill-switch
One command (trouble autonomy off, or the dashboard button) freezes the loop at the current stage — in-flight plays finish their current tool call, nothing new starts, everything after is recorded as pending. A single flag between "fully autonomous" and "fully supervised," instantly reversible.
