# QUORUM REVIEW — trouble PRD v2.3 (judge seat, read-only, evidence gathered 2026-09-16)

Machine: kernel 7.0.0-30-generic, Ubuntu 26.04.1, systemd 259, go1.26.5. All probes read-only; PSI trigger registrations were ephemeral in-kernel state freed on fd close.

## A. Load-bearing technical claims

A1. PSI poll()/epoll wakeups — PARTIALLY CONTRADICTED (privilege model changed, not the mechanism)
- Trigger semantics confirmed [measured]: open /proc/pressure/{res} O_RDWR, write "some|full <threshold_us> <window_us>"; one trigger per fd (second write → EBUSY); fd close frees the trigger; poll/epoll wakeup works (POLLIN observed on a registered root cgroup trigger).
- CONTRADICTION [measured]: on kernel 7.0.0-30, unprivileged trigger registration to /proc/pressure/* returns EINVAL for every valid parameter shape (threshold 1–1500000us, window 500000–10000000us, both some/full, with/without newline). Root succeeds with the same writes. /sys/fs/cgroup/io.pressure trigger: accepted as root, EACCES as uid 1000. Reads (avg10/60/300) work for everyone. Community kernel-list traffic (2026-07 selftest thread, reproduced on 7.0.0-28) confirms an unprivileged/privileged split in PSI trigger registration with a 2s-minimum-window rule for unprivileged writers [community] — but even the 2s-compliant write failed unprivileged on /proc/pressure here, so on this kernel the practical rule is: /proc/pressure triggers are root-only.
- Go without cgo: YES [measured-equivalent + inference] — the whole path is open/write/poll, i.e. syscall.Poll (stdlib) or epoll via x/sys/unix (pure Go, no cgo). No libsystemd involvement.
- Implication for the PRD: "epoll, 0% idle" is true only for a privileged daemon. SPEC must pin: trouble runs as root (or CAP) → triggers; otherwise → interval polling of avg values with a documented degradation. The PRD never states the daemon's user — that's a gap, not a detail.

A2. Sentry-compatible ingestion subset in Go — SUPPORTED, wrong citation
- Envelope format (header line + item pairs), DSN-derived auth, gzip, rate-limit headers (429 + Retry-After / X-Sentry-Rate-Limits) are documented protocol [official]; the legacy /api/{PROJECT_ID}/store/ endpoint is deprecated but explicitly kept server-side for compatibility [official] — the PRD's "envelope + store" subset is the correct, minimal pair.
- GlitchTip is real and Sentry-SDK-compatible [official/community] but it is Django/Postgres/Redis [community] — it proves the wire protocol is implementable, not the Go-single-binary claim. The right precedent is urgentry: a single Go binary on SQLite speaking the Sentry SDK protocol [community]. The PRD should cite that class, and SPEC should list the exact endpoint set: POST /api/{pid}/store/, POST /api/{pid}/envelope/, GET /api/{pid}/ (chunked release upload can be skipped; sessions/checkins/tracing are already deferred and their envelope item types must be 200-and-dropped, not rejected — SDKs send them mixed in envelopes [official]).

A3. journald following from Go without cgo — SUPPORTED with a clear MVP recommendation
- sdjournal (coreos/go-systemd) requires cgo and libsystemd headers [official pkg.go.dev]; there is no maintained pure-Go journal file reader, and systemd's own docs ask consumers not to parse journal files directly [community].
- Measured: journalctl -o json -f --output-fields=... works, cursor round-trip (--after-cursor) works, and this very host already runs a production journal-following monitor as a system unit (user-service-reset-monitor writing /var/log/.../journal-events.log) [measured] — the subprocess pattern is proven in the fleet's own environment.
- MVP recommendation: journalctl -o json -f --after-cursor <cursor> as a supervised child process (restart with cursor state on exit), uid must be in adm/systemd-journal [measured: works via adm group]. Reserve the sdjournal path as a cgo build-tag variant later. The HTTP gateway (systemd-journal-gatewayd) is not even installed here [measured] — do not make it the MVP path.

A4. systemd D-Bus unit-failure subscription from Go — FEASIBLE, pitfalls real
- coreos/go-systemd/dbus (godbus-based, pure Go, no cgo) implements exactly the JobRemoved/UnitNew/PropertiesChanged subscription the PRD needs [community/official source]. systemd 259 on-box [measured].
- Pitfalls SPEC must encode [
- Pitfalls SPEC must encode [official systemd D-Bus docs + community source]: (a) Subscribe() then StartUnit() ordering — subscribe BEFORE acting or you race the signal; (b) JobRemoved filters must match the returned job object or you react to unrelated jobs; (c) PropertiesChanged for org.freedesktop.systemd1.Unit carries SubState — that's the crash/restart signal, but it's only emitted for units you've subscribed to (systemd's private Subscribe rules); PropertiesChanged itself is broadcast but systemd's manager-level subscription gate is per-signal-source — SPEC must pin which of the two mechanisms is used and cover unit-set churn (units appearing/disappearing between subscriptions → re-subscribe sweep). (d) user vs system manager: hermes-gateway runs as a --user unit here [measured] — trouble must watch BOTH buses or explicitly declare system-only; that's an unanswered PRD question. (e) The D-Bus connection dying silently when systemd reloads — go-systemd handles reconnect poorly; a periodic sanity poll (systemctl show of a canary unit) is needed as the liveness check.

A5. Git worktree per hot-fix incident — SUPPORTED with two concrete footguns
- Worktree isolation semantics confirmed [official git-worktree docs]: a branch can be checked out in only one worktree (add refuses otherwise); each worktree has an independent index/HEAD → parallel foremen don't collide at the working-tree level.
- Footgun 1 [community, auto-worktree issue #176]: worktrees do NOT prevent corruption from simultaneous git commands on the shared object store — two foremen running gc/repack/branch concurrently can corrupt .git. SPEC must ban non-add/commit/worktree-remove git operations inside foreman worktrees (no fetch/gc/prune from the worktree; main checkout is the only place those run) and serialize worktree add/remove.
- Footgun 2 [measured, this box]: /tmp/hd446-prefix-wt is a live detached-HEAD worktree in /tmp — the fleet ALREADY does exactly this pattern (hermes-dagger has 4 worktrees). Conflicts are not theoretical: a scheduler foreman and a trouble hot-fix foreman can both create worktrees in the same repo; SPEC must pin a namespace prefix (e.g. /tmp/trouble-wt/<incident-id> or .git/trouble-worktrees/) and a cap on concurrent worktrees per repo, plus TTL cleanup so crashed incidents don't leak worktrees (the /tmp one is already an orphan class).
- "Cheap": true — files are checked out fresh but objects are shared; cost is disk for the checkout, not the history [official].

A6. htmx/templates dashboard at ~15MB — SUPPORTED, budget realistic but not automatic
- Direct on-box precedent [measured]: schedulerd (22MB binary) embeds htmx.min.js via go:embed and serves server-rendered templates + htmx partials — the identical stack the PRD proposes, in production here. A dashboard-light daemon at 10–15MB is plausible [inference]: stdlib net/http + embed adds ~2–4MB over a bare binary; the scheduler's 22MB includes the whole scheduling engine + SQLite. 
- The 64MB MemoryMax [PRD §11] is the binding constraint, not binary size: html/template parsing + htmx asset + JSONL ledger scans under concurrent dashboard requests will fit, but SPEC must pin RSS ceilings per subsystem and forbid mmap-ing whole ledger files for queries (stream, or maintain a compacted index — which the PRD calls "retention compacts quiet groups" but never specifies the query path over the JSONL: O(n) scan per dashboard render breaks at a few hundred MB of ledger).

## B. Spec-readiness gap scan (would force a worker clarifying question)

1. Storage schemas — NOT pinned enough. "Append-only JSONL" + §12 says the board is JSONL-canonical with parquet/DB caches, but the PRD never defines: file set (incidents.jsonl? groups.jsonl? one ledger.jsonl?), record envelopes (id/seq/timestamp/sig/source/payload?), the query mechanism over them (full scan vs sidecar index), compaction/retention mechanics (rewrite file? tombstones? — "append-only" contradicts "compaction" unless compaction = new file generation, which must be stated), fsync policy (a crash-observability daemon with un-fsynced ledger is a scandal waiting), and the single-writer rule (is the daemon the only writer, period — see C). SPEC needs: one ledger file schema, one event-type table, one index strategy, one compaction algorithm, one durability statement.
2. Identity/key formats — partially given. DSN example "http://pubkey@trouble-host:8643/7" pins shape but not: key length/format (Sentry uses 32-hex public key + 16-hex secret — compatibility says follow it), how keys are created/stored/rotated (trouble CLI? generated at init? file with what perms), token store for dashboard auth (random hex length, file location, one token or per-user?), and the sig format "{source}:{canonical-hash}" — hash of WHAT bytes exactly, which normalization (the PRD says "masks line numbers/addresses/PIDs" but not the algorithm or whether the mask set is versioned — sig stability across trouble versions is a silent-breakage class). Each is a day-one worker question.
3. Ladder state machine — underspecified. States are implied (recorded→playbook→research→agent→outlets) but: who advances (sensor event? timer? both?), can a rule pin the entry rung (it says "propose/execute per rule" — for the AGENT rung only), retry semantics per rung (playbook failed twice → escalate? re-run? cooldown?), the stabilization window ("stabilization" is referenced in §05 research but never defined — duration? measured from what?), and two-strikes suspension is per-sig or per-rule or per-daemon? All unpinned.
4. Module interface — direction given, contract absent. "descriptor + Go impl + tests" but no Go interface (method names, the 6-stage signature — does the daemon call authorize/validate/dryrun/apply/verify/audit as separate methods or one op with stages?), no descriptor format (Go struct? TOML? JSON schema?), no conformance test harness shape. The module SDK is the thing third parties build against; it must be frozen at v1 or everything after churns.
5. Skill artifact schema — example given, edges unpinned: sig binding exact form (example shows both a hash and a free-text journal sig — is the free-text form legal? then dedup guarantees weaken), versioning rules (version=3 — who bumps, what does a downgrade mean), compatibility (skill from hub runs on older satellite: what's the check?), conflict resolution (two skills match one sig), and the [play] TOML shown is actually invalid TOML as written in the PRD (array-of-tables syntax "- tool = ..." is not TOML — the example itself would fail a parser, a concrete spec-readiness smell).
6. Dashboard routes — not enumerated. Feature cards describe views, not paths. SPEC needs the minimum route table (~8-12 paths), the auth model per route class (read token vs write grants), and whether the API and dashboard share a mux. Also [measured]: port 8643 is ALREADY BOUND by hermes on this host and 8644 by implication adjacent to the hermes gateway's 8642 — the PRD's fixed port numbers collide with the fleet's own convention; ports must be configurable with defaults that don't collide (or be declared fleet-reserved).
7. The five topologies — the PRD gestures at them (§06c light mode, §12 proxy) but T1–T5 are never enumerated as such; see C for what's ambiguous per topology. Nothing in the PRD names hub/satellite protocol, addresses, or auth between trouble instances — the single biggest spec-readiness hole for anything beyond T1.

## C. Scale-design critique — five topologies

T1 single laptop: implied shape = one daemon, everything local, resolver=none default. What breaks first [inference from design]: the JSONL ledger under dashboard scans (see B6) and journal-follow throughput if the box is the stressed one (the monitor itself competing with the incident). Must decide NOW: the daemon must NOT be in the dependency chain of its own monitored services (no restart loops: trouble restarts payment-worker, payment-worker's failure kills trouble → mutual latch). The one MVP decision that prevents a rewrite: single-writer ledger with a stable record schema + sig format — everything else in T1 tolerates change.

T2 single cloud VM: shape = sentinel exposed (remote ingestion over public), dashboard token-authed. Breaks first: DSN public-key auth on a public interface — Sentry's DSN model assumes a relay/CDN in front; a raw Go server with public-key-only auth on :8643 is an unauthenticated write endpoint with quota (spam fills groups → dedup holds but quota math floods). Must decide NOW: whether remote ingestion requires the secret part of the DSN (Sentry SDKs send both) or a reverse-proxy mandate for public exposure; later is fine for T1 but the DSN validation logic (which parts are checked) is day-one code. Also: 429/Retry-After and X-Sentry-Rate-Limits header emission must be per-official-format or SDKs will hammer instead of backing off [official transport docs]. One decision: define auth level per bind address (loopback=public-key-ok, non-loopback=require-secret-or-proxy) — cheap now, brutal to retrofit.

T3 home lab 2-4 boxes LAN: shape = hub + light satellites (§06c) or full daemons cross-reporting — the PRD supports both and never says which is the default for "another box reporting in." Two competing mechanisms exist in the text: (a) remote app → hub DSN directly (§04b), (b) light agent → forward incidents up (§06c). These have different data models (events vs incidents), different auth (DSN vs ???), different failure modes. Breaks first: the undefined hub/satellite protocol — nothing specifies the up-forward format, its queue/spool depth on the satellite, or backpressure from the hub. Must decide NOW: one forwarding protocol (I'd say: satellite uses sentinel's own ingestion wire format to forward — one protocol, not two), with spool-to-disk bounds. Decide later: which box is hub (config, not code).

T4 Tailscale spread + phone dashboard: shape = T3 over tailnet, dashboard readable from phone. Breaks first: nothing new architecturally (Tailscale is just transport) EXCEPT the dashboard-on-phone claim (AC-19) collides with token auth on a long-lived mobile browser + the PRD's "loopback+unix-socket OR token" split — a phone can't do unix sockets, so token-over-Tailnet is the real path; session lifetime/refresh is unspecified. Also satellite→hub over Tailscale inherits T3's undefined protocol plus reconnect-queueing (AC-25 says offline-tolerant but queue bounds/eviction policy are unspecified — unbounded disk spool on a Pi is its own incident). Decide NOW: queue bound + eviction (e.g. drop-oldest with ledger note). Decide later: Tailnet-specific anything.

T5 many machines / regional hubs / customer-edge proxies: shape = hub-of-hubs + sentinel proxy relay (§12). Breaks first, in order: (1) skill-repo contention — every host pushing candidate PRs and pulling on interval from ONE git repo; git pull storms and merge conflicts on the skills repo at fleet scale are a known git pattern [inference]; decide later (webhook distribution, or release-tags instead of branch-pull). (2) hub saturation on the sentinel ingestion path — single Go server, single-writer ledger: ingestion is CPU (fingerprint hashing) + ledger fsync-bound; at N×10^3 events/s the fsync-per-event choice (B6) becomes THE ceiling; the quota math must be per-project-per-hub with a global cap or one customer's runaway app starves others through the shared ledger writer. (3) proxy spool (AC-27) — same unbounded-queue issue as T4, now on customer edges. The one MVP decision that prevents the T5 rewrite: the ledger record schema and sig format must already carry a host-id/origin field and a hub-id — retrofitting "where did this come from" into a signature space after 10 hosts share it breaks every dedup guarantee. Also: proxy→hub auth needs its own key class (proxy key ≠ project DSN key) — that's a day-one token-store schema question, not a T5 question.

Per-transition single decisions, compressed: T1→T2 = bind-address-scoped auth; T2→T3 = one forwarding protocol = the ingestion wire format; T3→T4 = queue bounds + token session model; T4→T5 = origin fields in sig/ledger + proxy key class. None of these is in the PRD today.

## D. Repeated-offense audit

- Gateway-drain kills in-flight work: the PRD has rename-over upgrades + OOM immunity [PRD §11] but does NOT address hot-fix foremen surviving a daemon death — a spawned worktree foreman is a separate process, so it survives, but the VERIFY WINDOW and PROMOTE gates live in the daemon; daemon restart mid-window = who owns the open incident state? SPEC must state: incident state is in the ledger, re-hydrated on boot, in-flight foreman tracked by PID+worktree path and re-adopted or explicitly orphaned-with-notification. Currently silent.
- ALL-GREEN silent data loss: "verify" in the PRD means "sig quiet for the window" — that is real, measurable verification (good, better than status-green). But the sensor path itself has no self-verification: if journald-follow child dies or the D-Bus connection wedges, the dashboard still renders and everything looks fine. The fleet's own scars (state-db-sentinel lying, board scans stale) say: every sensor needs a last-success heartbeat surfaced in the dashboard System view (the scheduler's board_wake watchdog-of-the-watcher [measured precedent in this repo's AGENTS.md] is exactly the pattern). PRD has "rule health (last fire, suppressed counts)" but not "sensor liveness." Gap.
- Stale binaries / version skew hub vs satellites: skill distribution is solved (repo pull), but SATELLITE BINARY version skew is unaddressed — a v1 light agent forwarding to a v2 hub with a changed protocol, or a v2 skill pulled onto a v1 agent (B5 compatibility, unanswered). SPEC must pin: skills carry a min_daemon_version and the forwarding protocol carries a version header; hub rejects with a readable error.
- Silent cron death / who watches trouble: the PRD never names the watchdog-of-the-watchdog. On this box that's systemd itself (Restart=always + watchdog notification via sd_notify, plus the mem-monitor/user-service-reset-monitor pattern already running [measured]). SPEC: Type=notify + WatchdogSec= on the unit, a canary rule that MUST fire (synthetic sensor), and an escalation driver that reports trouble's own health out-of-band (a dead daemon can't telegram about itself — so the unit's OnFailure= does it, or a second tiny unit). Must be explicit, not inherited.
- Private-/tmp class: PRD §08 pins worktrees but never says WHERE plays, skill candidates, or research briefs write. The fleet lesson (cron cwd landing in <fleet-home>, /tmp worktrees orphaning) maps directly: SPEC pins $STATE_DIR (~/.trouble or /var/lib/trouble) for everything persistent, /tmp only for worktrees with the TTL cleanup from A5. Currently unspecified.
- DSN/auth dialect traps: the PRD says env vs config precedence NOWHERE. SENTRY_DSN is an env var in the app's world (fine — that's client side), but trouble's own config precedence chain (file < env < flag? the scheduler fleet just standardized exactly this chain [measured, scheduler AGENTS.md budget-authority model]) is unstated, as is which of dashboard token / API token / DSN keys wins when both are present on a request. One paragraph in SPEC kills the whole class.

## E. VERDICT

TOP 5 fixes, ranked (where each lands):

1. Pin the PSI privilege model and daemon user (PRD §04a + SPEC sensors): kernel 7.x unprivileged /proc/pressure trigger writes return EINVAL [measured]; SPEC must declare the daemon user, the root/CAP trigger path, and the interval-polling degradation, or the core "epoll, 0% idle" claim is false on the target hardware.
2. Write the storage SPEC (SPEC-ledger): file set, record envelope, sig format + versioned normalization, fsync policy, single-writer rule, compaction algorithm, query/index path, origin+host-id fields for T5. This is the largest spec-readiness hole; every other subsystem reads from it.
3. Define the hub/satellite + proxy protocol as ONE thing (PRD §06c/§12 → SPEC-forwarding): reuse the sentinel ingestion wire format, add version header, spool bounds, eviction policy, proxy key class in the token store. Two forward paths in the PRD must become one.
4. Add the failure-observability spine (PRD §11 → SPEC-ops): sensor liveness heartbeats in the dashboard, daemon watchdog (sd_notify + WatchdogSec + OnFailure escalation), incident re-adoption after daemon restart (foreman ownership), config precedence chain (file<env<flag, one auth-wins rule). This closes every D-section recurrence.
5. Fix the schema-level details that will otherwise churn: valid TOML for the skill example + min_daemon_version + conflict rules (PRD §06c); the exact Go module interface + descriptor format frozen at v1 (§06); dashboard route table + non-colliding default ports (8643 is bound by hermes on this host [measured]) + bind-scoped auth (§04c).

Readiness paragraph: The architecture is coherent, the ecosystem fit is real (every integration named — board JSONL, task-router, router_spawn, worktrees, DuckBrain — exists and works on this box [measured]), and most load-bearing technical claims survive contact (PSI mechanism yes with a privilege caveat, journald-via-journalctl yes with on-box precedent, D-Bus subscription yes, worktrees yes with two named footguns, dashboard stack yes with an in-fleet production twin). But the PRD is a vision document wearing a spec's clothes: storage, identity formats, the ladder state machine, the module interface, and the entire hub/satellite protocol are named but not defined, and five of those definitions (fixes 1-3 and 5) change code that everything else sits on. Converting now would produce SPECs that get rewritten mid-build — the worker-question rate is still several per subsystem. With fixes 1-5 folded in first (they are PRD-level decisions, each a day or less of authoring), the SPEC-01..NN decomposition is straightforward: ledger, sensors, sentinel, dedup, ladder, tools/modules, skills, dashboard, flow/hot-fix, forwarding — roughly ten specs with clean seams.

BUILD WITH CHANGES — the changes: pin daemon user + PSI privilege degradation (1), author the storage/identity SPEC before any build (2), collapse the two forward paths into one versioned protocol (3), add the failure-observability spine and config-precedence rule (4), and fix the skill-example schema / module interface freeze / port collisions (5).
