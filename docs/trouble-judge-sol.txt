A. LOAD-BEARING TECHNICAL CLAIMS

A1. PSI poll/epoll on /proc/pressure/* — VERIFIED, with a hard-won pitfalls list

Documented semantics [official, docs.kernel.org/accounting/psi.html]: triggers exist since v5.2 (commit 0e94682b73bf) [community, kernel-internals.org]; format `<some|full> <stall us> <window us>`; window 500ms–10s; **unprivileged writers must use a window that is a multiple of 2s**; one trigger per fd (second write → EBUSY); trigger de-registers on close; notifications rate-limited to 1 per window; poll wakeup is POLLPRI; POLLERR means "source gone".

Measured on this box (all three /proc/pressure files are mode 0666, uid 1000):

    some 150000 2000000\n   -> OK      (2s window, multiple of 2s)   [measured]
    some 150000 2000000\x00 -> OK
    some 150000 2000000     -> EINVAL  <-- NO terminator; kernel overwrites the last byte with NUL
    some 1000 1000000       -> EINVAL  (1s: unprivileged requires multiple of 2s)
    some 500000 5000000     -> EINVAL  (5s, same rule)
    some 150000 400000      -> EINVAL  (<500ms min)
    some 3000000 2000000    -> EINVAL  (stall > window)
    some 150000 20000000    -> OK      <-- 20s ACCEPTED although the docs say 10s max (docs are stale)
    second write, same fd   -> EBUSY   [measured, matches docs]

So my first 40 minutes of "EINVAL on every grammar" was *my* bug, not the kernel's — and that bug is the real finding: **a strlen-sized write silently truncates the last digit; uncompensated it looks like a kernel that rejects the API.** Any Go impl must write `[]byte(fmt.Sprintf("some %d %d\n", stall, window))` (or +NUL) and treat EBUSY/EINVAL as distinguishable.

No-cgo feasibility: PROVEN [measured]. `syscall.EpollCreate1/EpollCtl/EpollWait` straight from stdlib (no cgo, no x/sys) on an armed trigger produced real wakeups at 875ms, 2.08s, 2.00s, 2.05s, plus an self-pipe shutdown wake. Caveats: a PSI fd is not pollable through the Go netpoller (`os.File.SetDeadline` won't work) → one dedicated goroutine + its own epoll set per trigger, plus an eventfd/self-pipe for clean shutdown (demonstrated). And: **poll on an UNARMED psi file returns immediately with POLLERR|POLLPRI** [measured, both Python 0x0b and Go 0x0a] — a naive "poll and read" loop is a 100%-CPU busy loop, which is a fine irony under the PRD's "epoll, 0% idle" banner. Also note the historical UAF fixed in 5.15/5.16 ("psi trigger destroyed while being polled", a06247c6804f) → pin a kernel floor, and probe grammar/limits at runtime rather than hard-coding doc constants.

A2. Sentry-compatible ingestion subset in Go — VERIFIED feasible; the PRD understates the SDK-side contract

[official, getsentry/develop]: store is `POST /api/<project_id>/store/` and is **DEPRECATED** ("All data should be sent to the /envelope endpoint"); envelope is `POST /api/<project_id>/envelope/`, newline-framed headers + items; auth via `X-Sentry-Auth: Sentry sentry_version=7, sentry_key=…, sentry_secret=…, sentry_client=…`; success = **HTTP 200 with body `{"id":"<event_id>"}`**; errors = 400 + `X-Sentry-Error` + `{"detail","causes"}`; compression = whole-envelope `Content-Encoding`; store limits 200KB compressed / 1MB decompressed; rate limiting = 429 + `Retry-After` + `X-Sentry-Rate-Limits: <retry>:<categories>:<scope>:<reason>:<namespaces>`, and the header **may also appear on 200s** (proactive backoff).

Precedents [community/official]: GlitchTip (Django+Postgres+Redis+Celery; "same SDKs, similar architecture"), Bugsink, and — the closest thing to the PRD's target — **urgentry**, a Go single-binary, SQLite-backed Sentry-compatible server claiming 218/218 documented API ops at ~52MB RSS under 400 events/s. Conclusion: the ingestion subset is a solved shape; trouble's sentinel is a re-implementation, and its only real differentiator is the ladder.

Three things the PRD gets wrong or omits:
- Modern SDKs speak **envelopes only**; treating store and envelope as equal-weight is stale.
- Envelope items you don't support (session, transaction, profile, replay, **client_report**) must be *tolerated and ignored*, not rejected — and `client_report` is exactly how an SDK tells you it dropped events. Ignoring it is how "no errors arriving" gets mistaken for health (see D2).
- Server-side quotas cause **loss, not backpressure**: "SDKs MUST honor 429 … Events … are to be discarded during the period that the rate limit is in place" [official]. The PRD's parenthetical "it floods only itself" is backwards — a quota breach destroys the very evidence the daemon exists to collect, so the loss policy (sample / drop with a counter / spool) is a spec decision, not an implementation detail.

A3. journald from Go without cgo — CONTRADICTION (partially): the binding path is cgo-only; MVP must be the subprocess

[official] coreos/go-systemd: the `sdjournal` package "wraps journald's native C API; consequently it requires cgo and the journal headers"; the pure-Go package is *write-only* (journal send). Community consensus in the only recent thread is `exec.Command("journalctl", …)`. That also keeps the PRD's "static Go daemon" promise (cgo breaks it unless you build against libsystemd.a).

Measured: `journalctl -f -o json -n 0 --after-cursor=<cursor>` follows correctly; a *malformed* cursor is a hard failure (`Failed to seek to cursor: Invalid argument`, rc=1) with zero stdout — so the follower must treat seek failure as "fall back to `--since=<last-ts>` + rescan", never as "no logs". `journalctl --disk-usage` = 1G here, /var/log/journal owned root:systemd-journal; unprivileged read works because opuser∈adm → **the daemon's install step must handle systemd-journal/adm membership (effective only after restart)**. Note also [official] cursors "do not uniquely identify an entry … string comparing cursors is not possible" → use `--after-cursor` replay + dedupe by `__CURSOR` equality, never ordering assumptions.

Recommendation for MVP: subprocess `journalctl` with persisted cursor + timestamp fallback + rotation/`--vacuum` tolerance, behind the same collector interface that later admits a cgo `sdjournal` build tag.

A4. systemd D-Bus unit-failure subscription via godbus — VERIFIED feasible, with four pitfalls and one blocking requirement

[measured, busctl introspect this box]: `Manager.Subscribe`/`Unsubscribe` exist, plus signals `JobNew`, `JobRemoved`, `UnitNew`, `UnitRemoved`. **There is no "unit failed" signal** — you either watch `org.freedesktop.DBus.Properties.PropertiesChanged` per unit object (unit names are escaped into object paths), or subscribe to jobs and then read the unit state, or poll `ListUnits`.

Pitfalls: (1) signals are not guaranteed/ordered → pair with a periodic `ListUnits` reconciliation (this is exactly what go-systemd's own interval-based subscription does); (2) systemd `daemon-reexec`/upgrade → `NameOwnerChanged` → re-`Subscribe` and reconcile, gaps are the failure mode; (3) `Subscribe` is read-only and allowed for plain users [measured: my `GetUnit` call reached systemd], but (4) **`service.reload/restart` is polkit-gated**: `org.freedesktop.systemd1.manage-units` = `auth_admin` / `auth_admin_keep` on this box [measured policy], so a non-root trouble daemon **cannot** perform the registry's service actions without an installed polkit rule (or running as root). The PRD's tool registry lists `service.reload/restart/stop/start` as ordinary D-Bus calls; that is an install-time contract, not a runtime detail. Bonus: `dbus: oomd` is plausible — `org.freedesktop.oom1` is documented and bus-activatable here [measured man 5 org.freedesktop.oom1 + busctl --list] — but systemd-oomd is **masked on this host**, so the sensor needs an explicit capability probe and a defined no-op.

A5. Worktree per hot-fix incident — VERIFIED with a collision problem the PRD doesn't see

Cheap and isolated: yes (shared object store, own index). Footguns, all real:
- concurrent `git worktree add` contends on `.git/config.lock` — a well-documented failure class for parallel agents [community: anthropics/claude-code #47266, #34645 — "Serialize git worktree add calls"].
- git refuses a branch already checked out elsewhere, refuses a path already assigned [official git-worktree docs]; submodules are not copied (each worktree needs `submodule update --init`) [official/community]; untracked build inputs (.env, node_modules) are absent → "the fix doesn't build" false negatives.
- **This fleet already has three conventions** [measured]: `<repo>/.worktrees/<task-id>` (kanban; found live in ~/<project>, ~/<project>, ~/<project>, ~/Kobayashi-Maru, ~/conscientiousness), `~/worktrees/<task-id>` with branch `wt/<ID>` (scheduler wave manifests/tests), and `hermes chat -w|--worktree` (the CLI flag, its own `git worktree add`). Trouble becomes a *fourth* spawner if it rolls its own.
- The fleet's own doctrine forbids that: the scheduler's AGENTS.md states "**Any future admission gate MUST live in SlotPool.spawn** — adding one anywhere else (evaluate, packers, watcher) is a design violation."

So the honest verdict: the mechanism is safe, the *authority* is not specified. Trouble must request the spawn from the scheduler (an audited priority class), and the worktree must be created by whichever single component already owns that repo — never by trouble hand-rolling `git worktree add` on a repo the scheduler's waves also touch.

A6. htmx/templ or html/template + embedded assets inside ~15MB — VERIFIED feasible (measured)

Built four variants on this box with go1.26.5, `-trimpath -ldflags="-s -w"`:

    A) net/http + html/template + embed(~100KB htmx/css/js assets)  7.99 MB
    B) A + godbus/dbus/v5 + golang.org/x/sys                       8.36 MB
    C) B + modernc.org/sqlite (pure Go)                           12.05 MB

Comparables [measured]: fleet schedulerd (Go, modernc sqlite, htmx server-rendered dashboard, 15 routes) = 22.4MB on disk, **35.9MB RSS**; hermes-dagger 21.6MB (67MB unstripped); boardctl 4.2MB. So: 15MB is achievable for a stdlib+few-deps daemon; it stops being achievable the moment you add SQLite + a TS/JS engine + evidence-heavy deps, and the budget is *binary*, not RSS. The dashboard stack choice itself is already validated in production on this fleet (schedulerd uses htmx + Go templates) — the PRD's default is right.

A7. (Not in the brief's list, but load-bearing in §05 ②½, §12 and open question #1) — CONTRADICTION

The PRD's research contract ("forward shape = fingerprint + stack + release + repro context; return = structured brief (hypotheses, similar cases, patch sketch)") **does not match the live Off-by-One API**. Measured today, live:

    GET  :8766/health -> {"status":"ok","uptime":"3h47m6s"}
    GET  /api/v1/stats -> 1716 problems / 1900 answers / 1872 verified / queue_depth 0 / solver_available true
    POST /api/v1/problems/discover {"problem_class":"svc-crash-loop","fingerprint":"sentinel:9f2c",...}
      -> 400 {"error":"invalid_request","message":"invalid JSON: json: unknown field \"fingerprint\""}

The lab is a **strictly-decoded, problem_class-keyed (kebab-case slug) verified-answer cache with an async submit queue**, not a hypothesis engine: discover takes `problem_class` (+env/lang/version) and returns a cached `solution`; submit needs `problem_class`, `cadence` (enum), `context` (object), and 400s on any extra top-level field; duplicate → 409; solver unavailable → 503; results arrive by polling the queue (~3m avg solve). Consequences for the PRD: the entire "fingerprint+stack → brief" mapping is work that does not exist yet (it is the *class-slug derivation* problem, and it is the hard part), there is no webhook push (polling is mandatory), and "research alone resolves it" means "the corpus already holds a verified answer for that class". Pin this in the spec or the research rung ships as fiction.

B. SPEC-READINESS GAP SCAN (what a worker would have to ask before coding)

The PRD is a strong *vision* document and a weak *build* document: it names mechanisms and defers every contract. A worker building from it verbatim would ask, at minimum:

1. Ledger (PRD "append-only JSONL"). Must pin: file layout (per-day/per-kind/per-hub), one record schema per type (incident / group / act / verify / play-run / research / skill-life), the write protocol (single writer per ledger — is the hub the only writer? O_APPEND? fsync per record? — see the measured 512 rec/s fsync ceiling), rotation + retention + compaction, torn-last-line recovery (this fleet has already had to repair corrupt JSONL stores), and the **query story**: "sentinel groups ranked by rate/trend/count" cannot be a linear scan of an unbounded file. Also: is the ledger the only store, or is an embedded index permitted (which changes the 15MB budget — 12.05MB measured with modernc sqlite)?
2. Identity/key formats. DSN: scheme policy (http vs https), host (see C2: must be a stable *name*, not an IP or a bind address), port, project_id range, public-key length/alphabet, whether a secret is allowed, generation, rotation, and how `trouble init` avoids the classic "DSN says 127.0.0.1 but the reporter is remote" trap. Dashboard token: format, storage (0600 file? systemd credential?), scopes, rotation. Sig format `{source}:{canonical-hash}`: exact hash function + truncation, the canonicalization field set per source, how SDK-supplied fingerprints are honored vs overridden, and a **sig format version** — normalization changes silently re-key the world otherwise.
3. Ladder state machine. States and transitions per rung, who may skip a rung (rules), retry semantics ("two-strikes suspension" — per incident or per sig per window?), stabilization window definition, global-vs-per-project "one agent at a time", per-rung timeouts, in-flight persistence across daemon restart (resume/replay/park), and the lock recovery path when the daemon dies mid-run.
4. Tool registry Go interface. The exact interface the SDK ships (name/schema/check/diff/apply/verify/rollback signatures), the JSON-schema dialect, the error taxonomy (retryable vs permanent vs needs-auth), the dry-run diff representation, the authorize model (which rule grants which tool), allowlist representation, and the rollback-record format. "6-stage contract" is a sequence, not an interface.
5. Module/plays semantics (the Ansible borrowing). This is a **hidden DSL**: the full field set of a play task (tool, args, when, retries, register…), the expression language for `when:` (operators, types, variable namespace, string/int coercion), the conformance-test harness definition, the check_mode diff format, and idempotency classification per module. Ship this as data-schema docs or workers will invent three dialects.
6. Skill artifact schema. `version = 3` implies versions, but: integer or semver? compatibility rules (min daemon version, required modules/tools)? how `sigs = [...]` matches (exact string vs glob)? conflict resolution when two skills match one sig? the candidate→review→promote state machine and who reviews by default (a PR? the dashboard? which actor lands in the audit ledger)? **the trust model for pulled skills** — a skill repo is remote execution via typed tool calls, so it needs signed commits / protected branch / allowlist / canary host, stated explicitly; and stats write-back (hosts updating `[stats]` means the distribution path is bidirectional and will conflict).
7. Ingestion contract (see A2). Endpoint list, methods, accepted auth forms, item-type policy (accept/ignore/reject), size caps, compression algorithms, response bodies, error shapes, and **the 429/quota math** (window, unit, per project, Retry-After value, whether X-Sentry-Rate-Limits is emitted on 200s) plus the loss policy.
8. Collector parser contract. Input mapping from journald JSON fields, file-tail rotation/truncation handling, multi-line error assembly (a Python traceback spans lines — what starts an event, what is continuation, what is the timeout), and the false-grouping rules.
9. Flow / direct board write. The fleet's real row schema (measured in ~/duckbrain/.coding-hermes/board/tasks.jsonl) is `{id,title,status,priority,complexity,depends_on,blocks,primary_model,primary_provider,fallback_model,fallback_provider,reasoning,capability_tags,worker_status,dispatched_at,completed_at,…}` written via boardctl (`create/update/event/validate`) with post-validate. The PRD must pin: id allocation, severity→priority mapping, how model/provider/reasoning/capability_tags get filled, whether trouble uses boardctl or raw append, and — critically — **whether the target project is registered/enabled in the scheduler**, because a JSONL row in a project the scheduler doesn't tick is a row nobody works (the PRD's "works even when the router is down" is only true if something else picks the row up).
10. Hot-fix spawn contract. Which endpoint, which actor, the brief field list, model/provider selection, budget/cooldown/weight interaction, the one-fix-per-sig lease, rollback-of-a-spawn, and the audit record shape.
11. Dashboard routes + auth. Enumerate the routes (the PRD gives four *views*, not paths), and pin auth: token scopes (read vs write), the loopback+unix-socket rule, CSRF for the POST actions, per-project scoping (mandatory before T2 multi-tenant), mobile/Tailscale exposure, and how a browser click becomes an actor in the audit ledger.
12. Autonomy modes. Exactly what each mode suppresses per gate (spawn? merge? promote? skill accept?), the kill-switch's in-flight semantics ("finishes its current tool call" → then what state?), who may flip modes, and whether shadow mode still writes candidate skills.
13. Lifecycle (almost absent). `Restart=`, `WatchdogSec=`, `sd_notify`, `OnFailure=`, drain-on-SIGTERM, rename-over upgrade semantics, config-schema versioning + migration, and hub↔satellite protocol version negotiation.
14. Security posture. Privileges (root vs user + polkit rule), the daemon's blast radius, token/DSN storage modes, and **the scrubbing spec — which the PRD does not have at all.** The design ships stack traces, journal tails, config versions and env into an append-only ledger that is then git-distributed (skills repo / DuckBrain), rendered in a dashboard, and auto-filed to GitHub. "Secrets never in the ledger" is stated as a promise with no mechanism (Sentry's answer is server-side data scrubbing with named rules). This is the one omission I would not let pass a design review: it is unauditable after the fact, because the ledger is append-only.
15. Sensor rules + normalization. Rule TOML schema, the condition language (shared with plays?), per-sensor normalization (the same function that feeds the sig core), cooldown/cap/storm semantics, and atomic hot-reload semantics (what happens to in-flight rules?).
16. Time. Which clock for windows (monotonic vs wall), jump handling, ledger timestamp format (fleet convention: RFC3339 UTC).

C. SCALE-DESIGN CRITIQUE — T1→T5

Ceilings I can quantify from this box: per-record fsync = 1.95ms → **512 records/s**; batched fsync = 1.94µs/record → 515k/s; substring scan of JSONL = 545MB/s (22.5MB in 40ms); `json.loads`-per-line = 19MB/s. Comparable daemon RSS = 35.9MB. Those four numbers decide most of C.

T1 (single laptop, no cloud). Breaks first: (a) the ledger under a chatty app — 512 rec/s per-record-durable means one noisy app can own the disk, and an unbounded JSONL fills a laptop; (b) the 64MB MemoryMax (see D2) kills the monitor exactly when the box is sick; (c) value with `resolver=none` (no AI) — if the ladder's only non-trivial rung is the agent, the no-cloud user gets a prettier log viewer; (d) secrets on a portable disk.
Decide now: no-root install (user unit + journald group), ledger path/rotation/retention, scrub rules, loopback DSN, and **"local mode = hub with zero satellites"** — same ingestion API, same record schema, same skill loop. That one decision is what keeps T1 a configuration of the T2+ design instead of a fork.

T2 (single cloud VM, public service + edge apps). Breaks first: (a) abuse — a public ingest key means anyone can POST: you need size caps, gzip-bomb protection (the 1MB decompressed limit is a *control*, not a doc line), connection/rate limiting, and per-key 429s; (b) loss semantics — 429 makes SDKs *discard* (A2), so "we're at quota" silently becomes "we have no data"; (c) TLS/hostname: SDKs verify certificates, and the DSN's host is baked into every deployed app — a hostname change (or an IP, or a bind address) is a fleet-wide outage of your ingestion, so the stable public FQDN and scheme are MVP decisions; (d) the dashboard's single-token, see-everything auth dies the moment there are customers.
Decide now: stable DSN FQDN + TLS strategy + reverse-proxy trust (X-Forwarded-For for per-client limits), per-project read scoping on the dashboard, and the quota-loss policy. Ceiling that bites next: hub saturation (single writer + single process) — the answer is batching + explicit sampling, not a bigger box.

T3 (2–4 boxes, one LAN; hub + light satellites). Breaks first: (a) not throughput — *trust*: satellites push findings up and pull executable skills down, so the protocol needs authentication both ways and a rule that satellites can never author skills; (b) double-counting: the spool-and-flush path re-sends after a blip unless every event carries an idempotency key and the hub dedupes on it (tie it to the sig core + an event_id); (c) version skew: a satellite with an old module set receiving a hub-pushed skill → refuse-and-record, never silently skip (see D3); (d) quota accounting must live hub-side; a satellite's local counter is unenforceable.
Decide now: one versioned hub/satellite envelope (event_id, project key, protocol version, ordered cursor, ack) + hub-as-sole-ledger-writer + skill/module version negotiation. Also hub addressing must be a configured name, not mDNS.

T4 (home lab over Tailscale, phone dashboard). Breaks first: (a) the auth model — "token or loopback+unix-socket" doesn't fit a phone, and pasting a token into a phone browser is how it leaks into history; tailnet identity (ACL/identity headers via `tailscale serve`) is the real answer; (b) node churn: off-LAN nodes change IPs — same stable-name requirement as T2, now with per-reporter DNS; (c) device loss: a phone/laptop satellite must carry an ingest-only credential, never a skill-execution one.
Decide now: dashboard auth as an **identity seam** (token provider now, tailnet/proxy-header provider later — one interface, two impls) and least-scope satellite credentials. Both are cheap in MVP and a rewrite otherwise.

T5 (many machines, multi-cloud, customer-edge proxies, fleet foremen). Breaks first: (a) the dedup core — "one signature space" is only true globally if the sig is content-derived and *versioned identically everywhere*; the moment sig normalization differs between hubs, dedup and verification both lie. Incident identity must be `(globally-stable sig, origin hub, hub-local sequence)` from v1, or a later federation console cannot merge histories; (b) cross-hub state: who owns an incident when two hubs see the same bug? (PRD defers the console but not the state model it implies); (c) the **skills repo becomes a code-deployment channel** — N hosts pushing candidate PRs means PR storms, review bottleneck and cross-host skew; needs protected branches, signed artifacts, staged/canary rollout, rollback, and a per-host pinned version; (d) edge proxies: real multi-tenancy — per-tenant auth, per-tenant quota, encrypted bounded spool, no cross-tenant leakage in the local spool; (e) scheduler contention: hot-fix foremen competing with fleet foremen for spawn slots, weight budget, cooldown fairness and model/provider lanes — trouble must be a *client* with its own priority class and budget accounting, and it must not bypass max_concurrent.
Decide now: federatable incident identity, skills-repo-as-release-channel discipline, proxy tenancy/spool model, and the scheduler admission interface. The single decision that buys all of T1→T5: **treat every deployment as "hub + N satellites", version both the ingest and the state/skill paths from record #1, and give every record a globally stable identity plus an origin.** Then the topology transitions are config, not surgery.

D. REPEATED-OFFENSE AUDIT (fleet scars vs this design)

D1. gateway-drain kills in-flight work. Measured fleet evidence: the nightly state.db vacuum mv-swaps the DB and restarts `hermes-gateway`, killing in-flight cron turns ("Interrupted by shutdown") — a known, owned gap. This box has 15 units with `Restart=always`, 9 `Restart=on-failure`, and **zero** `WatchdogSec=` [measured]. The PRD's §11 says "OOM immunity … rename-over upgrades — carried unchanged" and never mentions Restart/Watchdog/OnFailure. Answer the brief's question directly: trouble must NOT be a gateway child (no shared cgroup fate, no per-profile env inheritance), and "the daemon dies with the gateway" is exactly the failure to design against. Required: separate unit, `Restart=always`, `StartLimitIntervalSec=0`, `Type=notify` + `sd_notify` READY + `WatchdogSec` (so "hung" is a restartable state, not a green one), SIGTERM drain that flushes the ledger and parks (not abandons) the in-flight play, and an acceptance test that restarts hermes-gateway and proves trouble's uptime/ledger sequence continuity.

D2. ALL-GREEN silent data loss. "Verified = sig quiet + group flat + probes green" is absence-of-evidence logic, and the failure mode is self-inflicted: if ingestion is broken (DNS change after the fix, DSN rotated, app restarted with a different SDK, quota 429s discarding events), the group is flat *because nothing is arriving*. That is the same class as this fleet's state.db hole (verified by cron status, not by destination coverage) and the "sentinel `ok` lies" scar. Fix: positive controls — (1) a per-project canary event injected through the same ingestion path every N minutes, which must appear in the ledger within the window or the verification is *invalid* (not passed); (2) ingest `client_report` envelope items (SDKs report their own drops), so SDK-side sampling/loss is visible; (3) record the verification as an evidence tuple (events observed, canary seen, counters delta, window bounds), never a boolean. Also note the 64MB `MemoryMax` interaction: a cgroup memory limit is enforced by the **cgroup OOM killer** regardless of `OOMScoreAdjust` — so "OOM immunity (OOMScoreAdjust -500, MemoryMax=64MB)" is a contradiction; a Go daemon comparable to this fleet's runs 35.9MB RSS, so 64MB leaves ~28MB for gzip buffers, an in-memory group index and a flood backlog. Use `MemoryHigh` (soft, throttle) + a higher `MemoryMax` (hard, kill) + admission control + disk spool, and make sure memory *pressure* is itself a trouble incident. Separately, `OOMScoreAdjust=-500` on a shared host chooses who dies — it will be the gateway/foremen instead; pair it with a hard cap so trouble cannot export its own pressure.

D3. Stale binaries / version skew hub↔satellite. The PRD has a `version = 3` in the skill artifact and nothing about compatibility. Requirements: protocol version on every request, `min_daemon_version` + `requires_modules` on every skill/play, and a **refusal record** when a host can't execute (the fleet's own scar is silent no-ops: inert features that "work" by doing nothing). Dashboard must show a version matrix across hosts (the fleet's updater already prints one — precedent). Upgrade path: rename-over while a play is in flight needs a pinned state (park + resume), and the ledger must stamp the acting binary version so post-incident forensics can tell what actually ran.

D4. Silent cron death / watchdog-of-the-watchdog. Name it explicitly:
- `trouble.service` (watchdog: systemd `WatchdogSec` + notify).
- `trouble-escalate@.service`, wired via `OnFailure=trouble-escalate@%n.service`, which escalates through a path that does **not** depend on trouble (direct Telegram/SMTP/webhook), because "trouble is down" is precisely when troubke can't tell you.
- `trouble-heartbeat.timer` + an *external* checker (T3+: a satellite or a second host) that alarms on **ledger sequence not advancing**, not on process liveness — process-alive is the same lie as ALL-GREEN.
- Fleet precedent to copy: the scheduler's `board_wake` watcher has a heartbeat watchdog that emits a HIGH stall event when its own poll loop goes silent [measured, its AGENTS.md].

D5. private-/tmp class — where do plays/scripts/worktrees write? The PRD names none of it. Pin: ledger, spool, worktree root, skill checkout, and the `file.patch` backup/rollback dir. Then check the sandbox flags, because they interact: `PrivateTmp=yes` would put a worktree created under /tmp in a namespace **the spawned foreman cannot see** (it's spawned outside trouble), `ProtectSystem=strict` makes `git worktree add` fail without `ReadWritePaths=` for the repo + worktree root, and `DynamicUser=yes` breaks ownership of worktrees/secrets. Measured: no fleet unit currently uses PrivateTmp/ProtectSystem/DynamicUser (0 occurrences), so trouble's sandboxing is new surface — decide it deliberately. Note also /tmp here is not a separate mount (falls through to / with 549G free, rw, no noexec) [measured] — an unconfigured spool in /tmp is a disk-fill waiting for a flood. For T5's proxy, the spool needs fsync policy, a size bound, crash-safety, and encryption at rest.

D6. DSN/auth dialect traps (env vs config precedence). Requirements: one documented resolution chain (flags > env > file > defaults) with a `trouble config explain` that prints the resolved value **and its source** (fleet precedent: schedulerd's `budget_source` / `--show-config`), explicit separation of the daemon's own DSN from the app-facing DSN, `trouble init` generating a DSN whose host is reachable *from the reporter* (bind address ≠ advertised host is the classic silent-no-report), secrets in a 0600 EnvironmentFile and never in argv (fleet precedent: GAP-038 "gateway key never in argv"), the dashboard token never equal to an ingestion key, and — because SDK dialects differ (X-Sentry-Auth vs `?sentry_key=`, envelope-only modern SDKs, browser SDKs refusing http from an https page) — accept all documented forms and **record which form each project uses** in the ledger, so an interop gap is data instead of a mystery.

E. VERDICT

Top 5 fixes, ranked (each with its landing spot)

1. Rewrite the research rung against the real lab. PRD §05 rung ②½, §12, open question #1; new SPEC-04. Delete "fingerprint+stack+release → brief with hypotheses/patch sketch". Spec the actual contract: class-slug derivation table (the real work), `POST /api/v1/problems/discover` on `problem_class` first (cheap, cache-hit path), submit `{problem_class, description, cadence, context{}}` only on miss, strict decoder (no extra top-level fields), poll `/api/v1/queue/{submission_id}`, corpus-grep fallback because `found:false` ≠ absent, 409 = already queued, 503 = solver unavailable → degrade as the PRD already promises. Live proof it must change: `unknown field "fingerprint"` (400).

2. Add a scrubbing subsystem before anything is persisted. New SPEC-02 (safety), and one line in §11's guardrails. Ingest → scrub → ledger → issue/board, with named rules (env-var names, key shapes, bearer/token regexes, path allowlists, per-project redaction config), a "what was redacted" counter per event (never the value), and a hard rule that the *only* un-redacted credential in the system is a DSN public key. Without this, v1 writes secrets into an append-only, git-distributed ledger and files them to GitHub — irreversibly.

3. Pin the storage tier and its durability policy. New SPEC-01/SPEC-03 (§06 dedup core, §03 ledger, §04c dashboard "no database beyond the ledger"). Decide: JSONL as the audit log with a **batched group-commit fsync** (1.94µs/rec amortized vs 512 rec/s per-record — measured) and a bounded in-memory index rebuilt at start for groups/quotas/trends; explicit rotation + retention + compaction; torn-line recovery; single-writer-per-ledger (hub only); and either accept a rate ceiling with an explicit, counted sampling policy or admit modernc sqlite (+4.1MB binary measured; 35.9MB RSS comparable). This decision determines module layout, the 15MB budget and whether the dashboard's "rank by rate" queries are O(1) or O(file).

4. Fix the three host collisions before code exists. (a) Ports: **:8643 is already in use on this host by the uncensored Hermes gateway** [measured, `ss -tlnp`] — the PRD's sentinel default collides with the fleet's own service; move the defaults clear of 8642/8643, and give `trouble init` a bind preflight that refuses a taken port. (b) Memory: replace "OOM immunity (MemoryMax=64MB)" with `MemoryHigh` + `MemoryMax` headroom + admission control + spool (see D2). (c) Spawn authority: SPEC-08 must route the hot-fix spawn through the scheduler's single admission point (its own doctrine: "Any future admission gate MUST live in SlotPool.spawn"), with a priority class, budget accounting, one-fix-per-sig lease, and the worktree created by the component that already owns the repo — trouble must not be a fourth worktree convention (three already exist here [measured]).

5. Make "verified" positive and make trouble observable when trouble is the broken thing. SPEC-05 (verification) + SPEC-09 (lifecycle): canary-event verification + client_report ingestion + evidence tuples + a refusal record for unexecutable skills; `Type=notify`/`WatchdogSec`/`Restart=always`/`OnFailure=` escalation that doesn't depend on trouble; a heartbeat that alarms on ledger-sequence stall from a *different* host; and, in the sensor spec, the PSI arming rules measured in A1 (terminator, 2s-window rule for unprivileged, no-trigger = busy loop, per-trigger epoll goroutine + shutdown pipe) and the journald follower's cursor-failure fallback.

Is it ready to convert into a SPEC-01..NN suite + build plan now? Not quite — but it is one short revision away, and that is a much better position than most PRDs I get to judge. All six load-bearing technical claims verify as feasible on real hardware (PSI polling including no-cgo Go: proven with live wakeups; Sentry ingestion: solved shape with a Go precedent; dashboard/size: 7.99–12.05MB measured, and this fleet already runs htmx+Go templates in production; D-Bus/worktrees: feasible with named footing). The architecture is sound and the two hardest ideas are right: one signature space shared by every plane, and plays-as-data (idempotent, check_mode-d, conformance-tested modules) instead of a more powerful agent — that is precisely the "ability scales without freedom" doctrine this fleet has already paid for. What blocks spec conversion is not architecture but contract surface: ~16 areas in B that a worker would have to ask about, one factual error (the research API, A7), one missing safety subsystem (scrubbing, B14), and three collisions with the host it is meant to run on (ports, memory policy, spawn authority). Close those, freeze the PRD at v2.4, and the SPEC suite writes itself along the seams the document already implies.

Final line: **BUILD WITH CHANGES** — (1) re-spec the research rung against the live Off-by-One API, (2) add the scrubbing subsystem before any persistence, (3) pin the ledger's storage/durability tier with a data-backed rate ceiling, (4) resolve the port, memory-cap and spawn-authority collisions with the host fleet, (5) convert "verified" into positive evidence and give trouble a watchdog that doesn't depend on trouble.
