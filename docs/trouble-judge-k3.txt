# A. LOAD-BEARING TECHNICAL CLAIMS

## A1. PSI poll()/epoll wakeups on /proc/pressure/* — VERIFIED, with 3 corrections the SPEC must absorb

[official] docs.kernel.org/accounting/psi.html (fetched live): triggers are registered by writing `<some|full> <stall amount in us> <time window in us>`; the fd is then used with select()/poll()/epoll(); one fd per trigger; "Write operations to a file descriptor with an already existing psi trigger will fail with EBUSY"; windows 500 ms–10 s; "Unprivileged users can also create monitors, with the only limitation that the window size must be a multiple of 2s"; "Notifications to the userspace are rate-limited to one per tracking window"; the kernel's own example writes a NUL-terminated string and treats `POLLERR` as "event source is gone".

[measured] this host, uid 1000, CONFIG_PSI=y, CONFIG_PSI_DEFAULT_DISABLED unset:

- `/proc/pressure/{cpu,memory,io}` read fine (cpu some avg10≈0.6–1.0, io some avg10 0.06).
- Trigger write WITHOUT trailing NUL → **EINVAL for every variant** (incl. the documented `some 150000 1000000`).
- Trigger write WITH trailing NUL → accepted: `"some 100000 2000000"` → n=20, `"some 1000000 2000000"` → n=21, on cpu/memory/io alike.
- Unprivileged window rule confirmed: window 1 000 000 µs and 500 000 µs → EINVAL; 4 000 000 µs → accepted.
- Threshold 0 → EINVAL.
- Second write on an armed fd → `device or resource busy` (EBUSY, exactly as documented).
- Windows never-fire trigger: `poll(POLLPRI, 500ms)` → **n=0 after 500.52 ms** (blocks; a real wakeup source).
- Low threshold (1000 µs in a 2 s window): `poll(POLLPRI, 800ms)` → **POLLPRI (0x0002) at 729 ms**, no POLLERR. Real threshold wakeup works.
- epoll: `epoll_ctl(ADD, EPOLLPRI)` = 0 (ok), but `epoll_wait(500ms)` returned n=1 after **~2.04 s** (one tracking window) — the timeout was not honored as expected in my run. Treat wakeups as coarse and possibly spurious.
- fd with NO trigger: **347,378 zero-timeout poll hits in 200 ms** — always-ready (POLLPRI|POLLERR). Any daemon that arms its epoll loop with an unconfigured PSI fd busy-spins and can misread the documented POLLERR ("source is gone") as pressure.
- Go 1.26 stdlib has **no** poll wrappers: `syscall.Poll`, `syscall.PollFd`, `syscall.POLLPRI` are all `undefined` (compile errors measured). A stdlib-only program must hand-roll `syscall.Syscall(SYS_POLL, …)` + literal POLLPRI (my probe does exactly this, `CGO_ENABLED=0`, `statically linked`, 2.44 MB), or take `golang.org/x/sys/unix` (official Go-team module, no cgo, present in the local module cache).
- PSI fds cannot join Go's netpoller; a dedicated raw-epoll goroutine or one blocking poll goroutine per trigger is required — the PRD's "epoll, 0% idle" shape is achievable but is NOT a stdlib-netpoller shape. SPEC should say which one.

Corrections the SPEC must carry: (1) **NUL-terminated trigger writes** (a naive `WriteString` silently fails EINVAL); (2) unprivileged 2-s-multiple windows on Linux mean triggers can only express "X µs of stall in a 0.5–10 s window" — they CANNOT express the PRD's `psi: cpu some avg10=…` rule syntax, so **sampling is the source of truth and triggers are an accelerator only**; (3) wake ≠ threshold-crossed (rate-limited to one per window, and my epoll run returned at ~1 window despite a 500 ms timeout) → every wake must re-read the counters before firing a rule, and unarmed fds must never sit in the epoll set.

Verdict: the claim is TRUE with those three corrections. It is not cgo-dependent and it works on this kernel as an unprivileged user.

## A2. Sentry-compatible ingestion subset in Go stdlib + minor deps at single-binary scale — VERIFIED for the protocol; UNVERIFIED for SDK parity (and the PRD's path list is wrong)

[official] develop.sentry.dev, fetched live:
- Canonical ingestion endpoint is `POST /api/{PROJECT_ID}/envelope/`; "Sending event payloads to the `/api/{PROJECT_ID}/store/` API endpoint is **deprecated**". Envelopes "require Relay, which has been introduced in Sentry v20.6.0" — i.e. a server that accepts envelopes is implementing Relay's role.
- Auth: regular HTTP header, querystring, **or** an envelope header `dsn` carrying the full DSN; content-type `application/x-sentry-envelope` (text/plain, multipart, urlencoded also acceptable).
- Fingerprint override is a first-class official event field: "A list of strings used to dictate the deduplication of this event", with `["{{ default }}", …]` interpolation.
- Rate limiting: "we emit a **429** status code and specify a `Retry-After` header. In addition to `Retry-After`, Sentry (Relay) also includes … `X-Sentry-Rate-Limits`" of the form `retry_after:categories:scope:reason_code:namespaces`.
- DSNs are submit-only and designed public ("DSNs are safe to keep public because they only allow submission of new events"), matching the PRD's "DSN public keys excepted".
- [official] Relay (Sentry's own Rust ingestion service) operating guidelines: "At least **2 GB of RAM per Relay container**", multi-core, "4 CPU cores" for >100 req/s.
- [official] GlitchTip README (fetched): "open source, **Sentry API compatible** error tracking platform… partial fork/mostly re-implementation of Sentry's open source codebase before it went proprietary", Django 6 + Postgres, "**runs with as little as 512 MB of ram**", MIT.

[measured] my own stdlib prototype (`/tmp/trouble-probe/ingest`, `CGO_ENABLED=0`, static 9.7 MB incl. an httptest harness): gzip decode → JSON parse → sha256 fingerprint → JSONL append, 32×200 gzip'd POSTs to `/api/1/envelope/`:
- **6 400 events in 1.03 s = 6 199 req/s** with group-commit fsync (100-line batches).
- **1 972 req/s** with fsync-per-line. RSS 7.0 MB → 15.6 MB. Zero rejects, grouping collapsed 6 400 events → 1 sig.

Verdict: the *subset* is implementable in Go at single-binary scale — that part of the claim holds, measured. What is NOT proven and must not be claimed in a SPEC: SDK-compat *parity*. Real SDKs put attachment/session/span/transaction/minidump items in envelopes; Sentry's grouping algorithm is a large, config-driven surface (GlitchTip — a whole Django product — still diverges). SPEC must (a) pin the route table exactly — the PRD's `POST /api/{project}/event/` is not a Sentry path (canonical: `/api/{id}/envelope/`, legacy `/api/{id}/store/`), (b) define per-item-type handling: dispatch known items, **accept-and-counter unknown items, never reject the whole envelope**, (c) ship a compatibility matrix + a "known divergences" doc, (d) add a load AC (target req/s, p99, memory ceiling) — 2 GB/instance (Relay) and 512 MB (GlitchTip) are the reference points that make the PRD's 64 MB ceiling an unvalidated claim.

## A3. journald following with matched cursors from Go without cgo — FEASIBLE; recommend the subprocess, not the binding

[measured]:
- systemd/journalctl 259 here; `-o json`, `--after-cursor`, `--cursor-file`, `-f/--follow`, `--show-cursor` all present.
- `journalctl -o json -n 1` works **as uid 1000 without sudo**; took `__CURSOR=s=e2a54cd0…;i=1fd…` and `journalctl --after-cursor=<c> -o json -n 2` returned exactly **2 entries after it** — cursor-matched resume verified.
- libsystemd.so.0.42.0 exports `sd_journal_open/next/next_skip/seek_tail/wait/get_cursor` (nm -D), so a cgo binding is possible — and [measured] coreos/go-systemd v22.7.0's `sdjournal/journal.go:321` does `import "C"`. cgo breaks `CGO_ENABLED=0` static binaries, cross-compilation, scratch/musl images, and adds a libsystemd runtime dep.
- `systemd-journal-gatewayd` is **not installed** here (HTTP option is not free); no pure-Go journal reader in the local module cache (only zerolog/journald = send side).

MVP recommendation: **exec `journalctl -f -o json --after-cursor=<cursor>` as a supervised subprocess**, cursor persisted per rule/journald-namespace. No cgo, keeps the static binary, works on any systemd with json output. SPEC must add what the PRD is silent on: reader-death detection + restart with backoff (silent-death class); bounded queue + explicit drop/gap accounting (journalctl can outrun the consumer → the ledger must record a gap, not lose events quietly); journal rotation/vacuum vs cursor validity (record a gap when a cursor's file is gone); per-entry size caps and non-UTF8 `MESSAGE` handling (use `--output-fields`); and "never follow the whole journal by default on a busy host — unit-scoped rules first". Keep `sdjournal` behind a build tag as the documented no-subprocess option.

## A4. systemd D-Bus unit-failure subscription from Go (godbus) — FEASIBLE, no cgo; one fleet-specific trap that would have broken it silently

[measured] godbus v5.2.2, `CGO_ENABLED=0`, `statically linked`, binary 4.21 MB, RSS 4.4–6.5 MB after connect + 3 match rules:
- **System bus** as uid 1000: Connect OK, `Manager.Subscribe` OK (no polkit prompt), `JobNew` signal observed within 10 s.
- **User/session bus**: `Manager.GetUnit("coding-hermes-scheduler.service")` → `/org/freedesktop/systemd1/unit/coding_2dhermes_2dscheduler_2eservice`, `ActiveState="active"`, and `AddMatchSignal` for PropertiesChanged/JobNew/JobRemoved all OK; JobNew + JobRemoved observed in 10 s.
- **Trap [measured]:** this fleet's units are **user units** — `coding-hermes-scheduler`, `duckbrain-http`, `hermes-dashboard`, `canopy-*` all live in the user manager, and the *system* manager does not know them: system-bus `Manager.GetUnit("hermes-dashboard.service")` returned **"Unit hermes-dashboard.service not loaded."** A daemon that subscribes only to `org.freedesktop.systemd1` on the system bus will see nothing on this fleet and report ALL-GREEN. Trouble must watch the system manager AND each user manager it is configured for (resolving `$XDG_RUNTIME_DIR/bus`; a root daemon cannot read another user's bus without running in that uid's context).

Other pitfalls to pin: unit-path escaping (`-` → `_2d`, measured in the returned path); subscribe-then-reconcile (D-Bus does not replay state — enumerate failed units at startup or pre-daemon-start failures are invisible); `NameOwnerChanged` for `org.freedesktop.systemd1` (systemd restarts/reloads) → re-subscribe + resync; three arrival paths for one incident (PropertiesChanged + JobRemoved + journald) — that is precisely what the dedup core must merge, so the merge rule must be specified, not discovered; and "D-Bus down" must produce an explicit sensor-degraded ledger record, never silence.

## A5. Git worktree per hot-fix incident — SAFE PRIMITIVE, ALREADY FLEET-BLESSED; the risk is a second convention, plus disk

[measured] git 2.53.0, scratch lab `/tmp/wt-lab`:
- `git worktree add ../wt1 -b hotfix/inc1` → **7 ms**; second worktree on the same branch → `fatal: a branch named 'hotfix/inc1' already exists` (must use `--detach` or per-incident branch names); `--detach` works; 4 concurrent `git worktree add` via `xargs -P4` all exited 0 (no index/config-lock failures at this scale); hand-deleting a worktree dir leaves the registration `prunable` until `git worktree prune`.
- Cost = a **full checkout** of the tracked tree (shared `.git`). Measured working-tree sizes here: scheduler 68 MB, hermes-dagger 242 MB, task-router 464 MB, **duckbrain 8.9 GB**. "Fresh worktree per incident" is a disk decision, not a free one.
- Worktrees are **already in fleet use**: hermes-dagger 4 registered, task-router 4, duckbrain 1, schedulerd 1; the scheduler DB already models them (`tick_workers.worktree/branch/commit_sha`, `migrations.go`, `wave_manifest.go`).
- Local prior art: `~/gitreins-worktree-prd/index.html` — "GitReins Worktrees, PRD v1.0, 2026-09-12, **designed, not yet built**": one task → one tree, `branch gitreins/task/<id>` at `../<repo>-wt/<id>`, merge-back only on judge PASS, tree reaped on fail, and it documents the exact incident class trouble is aimed at: "**sibling-deploy wipes** … 3+ incidents this cycle; whole worker sessions lost".

Verdict: worktrees are the right primitive and the fleet already blessed them — so **trouble must NOT mint a second worktree naming/registry/reaper convention**; it must call the same spawn path and adopt the existing layout, or you get orphaned trees (measured: hand-deletion ⇒ prunable), branch collisions (measured), and 8.9 GB disk incidents. SPEC must add: per-repo mutex around worktree creation (shared `.git` serializes on gc/pack-refs), max concurrent worktrees + min-free-disk gate + `worktree_exempt` for huge repos, worktree base **not in /tmp**, reaping on promote/discard/verify-fail by the same code path, `git worktree prune` on boot, and a hard rule that the hot-fix foreman never runs `git checkout` in the main tree.

## A6. htmx/templ or html/template over embedded assets at ~15 MB — BUDGET IS OPTIMISTIC; use html/template+htmx, not templ

[measured]:
- The fleet's own comparable daemon: `coding-herms-scheduler/bin/schedulerd` = **22 479 138 bytes (22.4 MB)**, RSS **36 868 KB idle**, and per its AGENTS.md it is Go 1.26 + net/http + **htmx + server-rendered templates** + pure-Go sqlite. Its repo ships `internal/dashboard/static/htmx.min.js` = **47 755 bytes**.
- My builds: stdlib PSI probe 2.44 MB; +godbus 4.21 MB; net/http+gzip+json+sha256+httptest **9.68 MB** — all `CGO_ENABLED=0`, statically linked.
- `github.com/a-h/templ` is **not** in the local module cache → templ adds a codegen step (`templ generate`) to CI and to every consumer's build; html/template + a 47 KB vendored htmx needs nothing beyond stdlib.

[inference] realistic trouble daemon ≈ 18–25 MB binary, 35–60 MB RSS under load (ingestion measured 15.6 MB RSS for the trivial path; journal following, D-Bus, PSI triggers, rule engine, agent harness, tool registry and templates all add). Verdict: "~15 MB" is a stretch, and the PRD's guardrail pair (MemoryMax=64 MB + OOMScoreAdjust=-500) is not contradictory in cgroup-v2 terms (the score protects the daemon from its own children) but the **64 MB cap is below a measured comparable** — SPEC must define the budget as measured RSS with a load test and set the cap from it (I'd start 128–192 MB), or split sentinel ingestion into its own small unit. Choose html/template + vendored htmx + `embed.FS`, matching the fleet precedent; do not adopt templ for the MVP.

# B. SPEC-READINESS GAP SCAN — every question that would force a worker to guess

Counted from the PRD: 27 ACs (9 v1 + 8 v2.1 carried, 10 new), 13 MVP bullets, 5 deferred groups, 11 directives. It is a vision document; the following are the forced questions, grouped as the brief asks.

**1. Storage schemas (PRD: "append-only JSONL · everything")**
- No record schema: what is the per-line envelope (ts, kind, seq, incident_id, sig, actor, src, payload, schema_version)? One file per day/namespace or one per month? Is `seq` monotonic per file and who guarantees it?
- No fsync/durability policy. [measured] fsync-per-line ≈ p50 2.0 ms / p95 2.5 ms / max 5.0 ms ⇒ ~500 durable lines/s single-threaded; group-commit(100) measured 3.1× faster (6 199 vs 1 972 req/s incl. parse). SPEC must choose group-commit with a stated window and therefore a **stated crash-loss window**.
- No writer-ownership invariant (one writer per file; readers by offset) and no torn-last-line recovery rule (the fleet already has a jq-tolerant-line law for JSONL boards — reuse it).
- Retention: "retention compacts quiet groups; the ledger keeps the permanent record" — undefined. Define group compaction (counts kept, payload TTL/dropped, group row kept), ledger archival (shard/gzip/offload) and total disk budget. [measured] inputs for the math: a representative event is 1 064 B raw / 350 B gzip (3.0×); 1 M events/mo = 1.1 GB raw or 0.3 GB gzip; a ledger line in my bench = 74 B.
- Missing entirely: **PII/secret scrubbing**. "Secrets never in the ledger (DSN public keys excepted)" is asserted, never specified — yet the daemon ingests arbitrary SDK payloads (auth headers, DSNs-in-envelopes, tokens in exception messages) and journal tails. SPEC needs a scrubber (pattern list, `sendDefaultPii` semantics, redaction tests). This is the highest-liability gap in the PRD.

**2. Exact identity/key formats**
- DSN shape must be pinned to Sentry's real grammar: `{PROTOCOL}://{PUBLIC_KEY}[:{SECRET_KEY}]@{HOST}[:{PORT}]{PATH}/{PROJECT_ID}`, and critically **what PATH is** — SDKs append `/api/{id}/envelope/` themselves, so the DSN path must end at the base, not at `/api`. The PRD example `http://pubkey@trouble-host:8643/7` is ambiguous about whether `7` is a numeric project id or a slug, and whether a prefix is allowed.
- Key/token stores: where do DSN keys live (file? sqlite? perms?), how are they rotated/revoked, is there a secret_key? Dashboard/API token: single token or scoped tokens, hashed at rest, file path, reload semantics.
- Sig format `{source}:{canonical-hash}` needs: hash algorithm, source enum, per-source normalization spec **with test vectors**, and a **normalization version** carried in or alongside the sig (otherwise a normalization change silently splits groups — and in T3/T5 that happens across hosts and across skill versions).
- ID formats: incident/group/task/skill IDs need prefix + allocation authority. The fleet has already been bitten by duplicate-ID rows (gitreins PRD: "9 duplicate-ID rows — the known boardctl debt class") — do not let workers invent this.

**3. The ladder state machine**
- No state list and no transitions. Needed: recorded → playbook_attempted → (research_requested → research_returned) → agent_running → output → action_pending → verifying → resolved | escalated | suppressed | quarantined, with the exact edges, timers/leases, and who may skip rungs (research optional; playbook may resolve outright; agent may be skipped when research is confident — the PRD says all three informally, none formally).
- Retry semantics per rung: playbook `max_runs`, agent "two-strikes suspension", verify-fail → rollback + reopen (new incident or reopen the same one? — decides dedup behavior), and re-entry on recurrence after resolution.
- Concurrency: "one at a time" — globally per host, or per project? Where is the lease, and how does it not become the fleet's known spawn-overlap bug (the scheduler had to add "enqueue-first + recheck" after overlap pulled month-old sessions into one tick).
- **Shadow-mode contradiction (must resolve before SPEC):** "shadow (default): everything runs — detection, research, plays, even hot-fix foremen — but PRs stay unmerged and promotions wait." If plays execute `service.reload` / `config.set` in shadow mode, the default is not safe. Pin: shadow = check_mode-only for mutating tools, with an explicit list of read-only exceptions — or rename the default and say it mutates.

**4. The tool registry's Go interface**
- The PRD describes the contract (authorize → validate → dry-run → apply → verify → audit) but ships no types. SPEC must include the actual Go interface the SDK exposes — e.g. `Descriptor()` (name, version, JSON schema, required scopes, idempotency class, check_mode support, timeout), `Check(ctx, args) (Diff, error)`, `Apply(ctx, args) (Result, error)`, `Verify(ctx, args) (VerifyResult, error)` — plus the error taxonomy (transient/permanent/policy-refused), the diff representation, and the conformance-harness API (AC-23 needs a callable harness, not a promise).
- Define per-module "verify" (who decides success), rollback semantics for non-invertible actions, and the do-not-touch enforcement surface (registry layer — the PRD says it, but the protected-path/unit list format is unspecified).

**5. Skill artifact schema (and a direct contradiction)**
- Fields/versioning: what is immutable, allowed version steps (PRD shows `version = 3`), what happens when a bound sig changes, `min_daemon_version`, module deps, play schema version, review/approval record.
- **Contradiction:** the SKILL.toml example carries `[stats] applied/success/last_used` marked "live, updated by the daemon" *and* the artifact is distributed via a git repo. Live-mutating fields inside a git-distributed immutable artifact guarantee merge conflicts and PR noise on every host. SPEC must split: artifact (immutable, from repo) vs stats (local ledger/DB).
- Distribution trust model is absent and this is the scariest surface in the PRD: in `autonomy=full` a pulled skill executes tool calls → **skill distribution is fleet-wide remote code execution**. Required: signed artifacts + a config-listed signer key, an allowed-module allowlist per skill, canary/staged rollout, per-host approve policy, and `min_daemon_version` gating.

**6. Dashboard routes + auth model**
- Minimum route list is missing (the PRD names views, not paths). Pin at least: `/`, `/incidents`, `/incidents/{id}` (evidence bundle + tool-call audit), `/groups` + `/groups/{id}` + release-diff, `/issues`, `/flow/hotfix/{id}`, `/breakers`, `/rules`, `/budget`, `/api/health`, plus the partial endpoints (htmx). AC-19's "live incident appears within 2 s" forces the choice: SSE endpoint or 1–2 s polling — pick one and specify it.
- Auth: "token (same store as the API) or loopback+unix-socket", "same authorization as the CLI" — define the ACL (token scopes? a policy file?), CSRF for POST actions, exactly where the token may appear (never a query string on a phone over Tailscale — the fleet's own auth-dialect history proves this bites), and the bind matrix (loopback/tailnet/public) with a default-deny.
- [measured] port reality check: **`:8643` is already occupied on this box** by the uncensored-profile Hermes gateway (`python -m hermes_cli.main --profile uncensored gateway run`, pid 2028572); `:8642` by the default gateway; `:9090` schedulerd; `:3000` duckbrain. The PRD's default ingestion port collides on its own reference host. Ports must be config-driven with a **startup collision check that fails loudly**.

**7. The five topologies**
- The PRD describes T1/T2 (local + remote DSNs) and T5 (proxies, hubs, light mode) in prose but constrains none of the protocol: forward format, auth between satellite and hub, spool path/format/caps, idempotency keys, clock-skew policy, who mints canonical IDs, whether the hub is the only ledger writer, and how satellites discover/register. Without that, T3/T4/T5 are unimplementable and T1 code will be rewritten. See C.

**Additional gaps not in the brief's list but forced:**
- **Verification semantics** (the PRD's weak point): "sig quiet + group flat + probes green for the window" is absence-based evidence. It does not say *which hosts* must be quiet, nor what happens when a reporting host is offline/uninstalled — a service that stops reporting looks identical to a service that stopped failing. SPEC needs per-source liveness expectation + gap records + "the negative was observed by N of N expected sources".
- **Outlet/driver interfaces**: the 4-method issue contract (`EnsureBySig/Comment/Close/Healthcheck`) has no types (inputs/outputs, dedup window, idempotency, backoff, rate limits, partial failure), and no rule for "driver down → spool and replay, and record the gap".
- **Board write contract**: exact row schema, ID allocation, the comment/cross-ref path when a sig already has an open row, atomic append rules for git-tracked JSONL (append-only, never rewrite — the fleet's law), and coordination with the scheduler's boards (which are read by a live daemon).
- **Hot-fix spawn contract**: which spawn path (the fleet's `<fleet-home>/scripts/router_spawn.py` is the documented router entry), the exact CLI/flags, allowed_repos/unit_repo_map validation, what happens when the gateway/spawn infrastructure is down (queue? drop? — currently unspecified, and "spawn fails silently" is the worst outcome for this feature), and who observes the verify window on which hosts.
- **Rate/quota units**: per-project quota is "per project" with 429+Retry-After, but units (events/min, bytes/day), body-size caps, concurrency caps, the client-sampling interaction (`sample_rate` honored where — client, server, both?), and disk-quota backpressure are all unspecified.
- **Autonomy gate matrix + kill-switch boundary**: "full = zero humans in any loop" needs a per-stage gate table (detect/research/play/agent/spawn/merge/promote/skill-accept), and "kill-switch freezes in-flight plays after their current tool call" needs a defined checkpoint granularity plus what "pending" means and how resume works.
- **Upgrades/on-disk compatibility**: rename-over upgrades are stated, but a versioned append-only ledger read by old and new binaries needs `schema_version` + forward-compat read rules + a downgrade policy. [measured] live version skew exists in this fleet: the running schedulerd binary is built 03:47 while repo HEAD is 03:55 the same morning.
- **Off-by-One research contract**: the PRD itself flags it as open; SPEC must pin request/response schema, timeouts, idempotency, cost accounting, and the "lab unreachable" ledger record (AC-20 partly does this).
- **Testing gaps**: ACs are prose. The build needs numeric thresholds (ingestion req/s + p99, RSS ceiling, dashboard latency, dedup rates, storm caps, verify-window durations) and an explicit "unverifiable as written" list.

# C. SCALE-DESIGN CRITIQUE — THE FIVE TOPOLOGIES

Cross-cutting ceilings first ([measured] where numbers appear):
- **Single-writer ledger**: fsync-per-line ≈ 500 durable lines/s; group-commit(100) 3.1× better. One writer per file is the hard invariant; multi-host aggregation must funnel to one hub writer or shard by authority.
- **Hub saturation**: trivial ingest path measured 6 199 req/s; add grouping, rules, outlets, agent runs, dashboard, journal following, and expect an order-of-magnitude less. Sentry's own reference is 2 GB/Relay instance, GlitchTip 512 MB — a 64 MB single Go process is a *small* hub, which is fine if the SPEC says so.
- **Skill-repo contention**: N hosts × daily candidate PRs; [measured] the artifact's live `[stats]` fields make every host a writer to the same file.
- **Worktree disk**: full checkout per concurrent incident — 68 MB / 242 MB / 464 MB / **8.9 GB** measured on four fleet repos.

**T1 — single laptop, one box, no cloud.** Implied shape: daemon as a user unit, DSNs over loopback, dashboard on loopback or SSH tunnel. Breaks first: **the daemon shares the box with the patient it is diagnosing** — PSI is system-wide, and a storm plus an agent run plus the incident compete for the same CPU/disk; second, disk: [measured] /tmp already holds 245 222 entries here and the fleet habitually writes briefs/logs there. Decide now: single-writer ledger + state root (`~/.local/state/trouble`, 0700, never /tmp) + disk budget/retention + trouble is its **own unit with its own Restart/KillMode**, not tied to the gateway's lifecycle. Later-ok: HA, multi-tenant.

**T2 — single cloud VM, public service + edge apps.** Implied shape: `:8643` facing the internet (or a proxy), `:8644` admin, public DSN keys = anyone can post to a project. Breaks first: **abuse/bounds** — an unauthenticated public ingest with only per-project quota is a disk/CPU DoS surface; the fleet's own scars say public exposure is live in this environment (a *:3030 public forgejo with DISABLE_REGISTRATION=false sat in the stack). Decide now: pre-auth resource bounds (max body, max envelope, per-IP/project rates, concurrency cap, disk quota with a defined backpressure: 429 vs spool vs drop-with-counter), TLS termination model (does the daemon speak TLS or sit behind a proxy?), and the pinned auth model (public DSN + optional per-project token). Later: HA/multi-region.

**T3 — small home lab, 2–4 boxes on one LAN (hub + light satellites).** Implied shape: hub full daemon; satellites = sensors + sentinel ingest + skill execution + forward UP. Breaks first: **hub SPOF + flush-after-recovery** — satellite spools grow while the hub is down, then thunder on recovery; second, **identity** (satellite-created incidents vs hub canonical ids) and **clock skew** (verify windows and cursors are time-based). Decide now: the forward protocol (envelope schema, auth, idempotency key, spool format + size cap, backpressure), **hub-mints-ids** authority with a local↔hub mapping, hub = only ledger writer, and a sig-normalization **version** that travels with the sig so split groups can't happen across versions. Later: mesh/multi-hub.

**T4 — home lab over Tailscale (off-LAN, phone dashboard).** Implied shape: ingestion + dashboard over the tailnet (this fleet already runs tailnet side-doors: [measured] `duckbrain-tailnet-socat` maps 100.64.0.1:3001 → 127.0.0.1:3000). Breaks first: **auth on a phone browser** (token in a URL is a leak; cookie/Bearer only) and **identity/trust zoning** — node renames/re-keys break hostname-based identity, so identity must be a stable node id; also payload size/latency for the dashboard and the fact that off-LAN nodes make "quiet for the window" ambiguous. Decide now: bind matrix + trust zones (each source tagged loopback/lan/tailnet/public; quota and verification windows aware of zone), dashboard auth as header/cookie, node identity by stable id, and small-payload dashboard design (htmx partials over SSE/compact JSON). Later: mTLS/zero-trust.

**T5 — many machines / multi-cloud (regional hubs, customer-edge proxies, fleet foremen).** Implied shape: regional hubs + proxies at edges + central foremen + skill distribution. Breaks first, in order: (1) **grouping authority** — the same bug on 200 machines must collapse to one incident, which requires deterministic sigs across all hops and hub-side grouping; (2) **skill distribution as code execution** (see B5) plus repo contention from N hosts pushing candidates; (3) **retention/quota math** — you cannot keep raw payloads for a fleet (measured: 1.06 KB/event raw, 350 B gzip → 1 M events/mo = 1.1 GB raw / 0.3 GB gzip, per project class), so define aggregate-and-drop (counts forever, representative payload per group with TTL) and per-tenant quotas in the proxy.
**The one decision made once in MVP that prevents a rewrite for every T1→T5 transition:** make the pipeline **spool-and-forward, hub-authoritative and idempotent from day one** — every component writes to a local durable queue keyed by a stable idempotency key (sig + normalization version + source id); only the hub mints canonical ids and writes the canonical ledger; everything downstream (dashboard, outlets, verification) reads the hub. Do this in T1 and T2–T5 are deployments; skip it and every topology change is a data-model rewrite.

# D. REPEATED-OFFENSE AUDIT — do the fleet's scars recur here?

**1. Gateway-drain kills in-flight work → does the daemon die with the gateway?** [measured] `hermes-gateway.service` (user): `Restart=always`, `KillMode=mixed`; cron work runs in *transient scopes* (`hermes-worker-cron-*.scope`, `hermes-worker-proc_*.scope`) so a unit restart does not kill them directly — the real fleet scar is the nightly state.db swap + `systemctl --user restart hermes-gateway` (~04:04) killing in-flight turns ("Interrupted by shutdown", "state database file was replaced"). **Required SPEC line:** trouble runs as its own unit with its own restart policy, never shares the gateway's state or lifecycle, and keeps a durable local spool so gateway-down windows do not create ledger holes. **Second-order (missing entirely from the PRD):** the hot-fix spawn goes through the fleet spawn machinery (the gateway) — define spawn-failure semantics (queue + bounded retry + a `spawn_pending` record). As written, "instant foreman" silently degrades exactly when the fleet is sick, which is when trouble matters most.

**2. ALL-GREEN silent data loss → is "verified" real verification?** [measured] the fleet's own precedent is a watchdog born from this class: `EVAL-STALL: last eval 5m0s ago with 0 running ticks … misses=1` (and 235 `EVAL-ZERO-SELECT` lines) in `scheduler.log` — "the loop looked fine while nothing was happening". Trouble's verification is absence-based, so it recurs by construction. **Required SPEC line:** per-source liveness/heartbeat + last-event-age, explicit gap records for every collector/journald/PSI dropout, and verification phrased as "the negative was observed by N of N expected sources, all alive for the whole window" — not "nothing appeared".

**3. Stale binaries / version skew hub↔satellite.** [measured] live skew on this box: running schedulerd built **03:47**, repo HEAD **03:55** same day. The fleet maintains version-injection and binary-freshness skills precisely because "dev (unknown)" caused repeated confusion. **Required SPEC line:** version + git-sha + build time stamped in every binary, exposed on `/health` and the dashboard; skills/plays declare `min_daemon_version` + module deps; the hub refuses (or quarantines with a ledger record) pushing skills to satellites below the floor; a `fleet_version` surface exists. Without it, the headline skill-learning feature has no safety gate.

**4. Silent cron death → who watches trouble itself?** The PRD has **no self-watchdog AC**. The fleet's convention is a named watchdog per subsystem ([measured] `canopy_stack_watchdog.sh`, `cube-watchdog.sh`, `chs-http-restore-watch.sh`, `<project>-loader-watchdog.py`, `fleet-policy-test-watchdog.sh`) plus in-process heartbeat watchdogs in schedulerd (eval-stall, board-wake stall with a 30-minute re-emit throttle). **Required SPEC line:** a systemd timer / tiny external probe that checks `/health`, ledger freshness, and per-source last-event-age, alerting through a path that does not depend on trouble being alive (trouble cannot page about its own death) — `Restart=always` + `OnFailure=` + a heartbeat file whose staleness a cron checks; and a minimal ingestion-to-alert path that still works when the dashboard/agent is wedged.

**5. private-/tmp class (where do plays/scripts write?).** [measured] `/tmp` on this box holds **245 222 entries** and is world-writable; fleet worker briefs and logs live there today (`/tmp/trouble-judge-brief.txt`, `/tmp/tr036-brief.txt`, `/tmp/hd482_worker.log`, `/tmp/dfbunker5/`, `/tmp/dogfood-<project>/usep/`). The PRD's `file.patch` mentions allowlists/backups but defines no state root. **Required SPEC line:** state root (`~/.local/state/trouble`, 0700), per-incident run dirs, worktree base shared with the gitreins convention (never /tmp), spool dir with size caps + fsync policy, backups dir, cleanup on promote/discard — and extend the no-secrets rule to *bundles* (journal tails and SDK payloads carry tokens; the ledger is not the only leak surface).

**6. DSN/auth dialect traps (env vs config precedence).** [measured] live, in one fleet: Hermes gateway `:8642` = Bearer only (401 with no auth, 401 with `x-api-key`); DuckBrain `:3000` = `x-api-key` for its API (`POST /mcp` → 401 without it; `/health` open); schedulerd `:9090` = **no auth at all** (loopback); and `:8643` — the PRD's default ingestion port — is **already taken** by the uncensored-profile gateway. **Required SPEC line:** pinned precedence (flag > env > config file > default) with a resolved-config dump endpoint (`--show-config` / `/api/v1/config` + a provenance field for each value, copying the scheduler's `budget_source` pattern); pinned DSN auth acceptance (header, querystring, envelope-header `dsn`) with required-vs-optional fields; dashboard/API token model decided once; startup port-collision check that fails loudly.

## TOP 5 FIXES (ranked, with the exact landing spot)

1. **Cut v0.1 to one vertical slice and freeze the rest as "no ACs may reference the deferred column".** Land in PRD §10 + a new SPEC-INDEX that binds each SPEC to its ACs. v0.1 = sensors (PSI *sampling* + journald follow + D-Bus failed-units) + sentinel store/envelope subset with gzip, DSN auth, fingerprint override, quota/429 + generic JSON endpoint + collector parsers (go-panic/py-traceback only) + ledger + dedup core + tool registry (6-stage, ~3 modules) + one issue driver + dashboard (≈8 routes + SSE) + hot-fix worktree spawn (config-gated OFF by default). Defer to v1.0: module SDK + plays library + skill loop/distribution + light-mode offload + sentinel proxy + `autonomy=full` + research driver (keep the interface, ship `none`). Rider: pin shadow mode = check_mode-only for mutating tools. Reason: 27 ACs spanning four products (error tracker, config-management runner, self-improving skill distribution, autonomous hot-fix fleet) is not an MVP.
2. **Write SPEC-DATA before any code: the durable data model.** Land as SPEC-02 (new), covering ledger record schema + `schema_version` + torn-line recovery + single-writer invariant + **group-commit with a stated loss window** (measured basis: 500 fsync/s vs 6 199 events/s group-commit) + ids + sig normalization spec with test vectors **and a sig normalization version** + retention/compaction/archival + scrubbing/redaction + state-root layout. This is the fix that prevents the T1→T5 rewrite and the fix that stops four different workers inventing four id/sig formats.
3. **Make verification evidence-based, not absence-based.** Land in PRD §05 rung ①, §08 "Verify", and the AC text of AC-21/24/26: require reporter liveness for the whole window, per-source last-event-age + heartbeat expectations, explicit gap records on any sensor/collector dropout, and multi-host verification stating *which* sources must be quiet. Reason: D2 — this is how the ALL-GREEN class recurs, and trouble's whole promise is "it gets fixed, verified".
4. **Immutable, signed, staged skill/play artifacts; stats move out of the artifact.** Land in PRD §06c (rewrite the SKILL.toml example) + SPEC on distribution: artifact fields (name, version, sigs, play ref, guards, provenance, `min_daemon_version`, `allowed_modules`) are immutable; local stats live in the DB/ledger; distribution is signature-verified with a config-listed signer, canary host first, per-host approval policy, and `autonomy=full` may only auto-accept signed skills above a success threshold. Reason: today the artifact is a merge-conflict generator *and* an unsigned fleet-wide code-execution path.
5. **Fix deployment guardrails before features.** Land in PRD §09/§11 + new SPEC-OPS: config precedence + a resolved-config endpoint with per-value provenance; version/git-sha/build-time stamping on `/health` and the dashboard; **port collision check at startup** (measured: `:8643` is taken on this host); state root per D5; self-watchdog per D4 (systemd `OnFailure=` + external heartbeat probe + a minimal alert path independent of the dashboard/agent). Reason: every one of these is a measured, already-paid-for fleet lesson, and each is cheap now / expensive later.

## READINESS

No — not as written, and the reason is not the technology. The technical spine survives contact: PSI triggers and poll wakeups work here without cgo (with three corrections), godbus subscriptions work against both managers with no cgo, journald following with matched cursors works unprivileged via the subprocess route, worktrees are safe and already fleet-blessed, and I measured a Go-stdlib Sentry-shaped ingester doing 6 199 req/s at ~15 MB RSS static. But v2.3 is a vision document wearing a PRD's clothes: 27 ACs across four products, and the spec-readiness scan turns up roughly twenty forced questions — the ledger/durability/r etention model, id and sig formats (with a version), the ladder's states and shadow-mode semantics, the tool interface, the skill artifact that both mutates and ships via git, dashboard routes/auth, the hub↔satellite protocol, PII scrubbing, quota units, self-watchdog, config/auth dialects, and the definition of "verified". A worker handed this today would invent all of those, and the expensive-to-change ones (writer ownership, ids, sig versioning, artifact shape, forward protocol) are exactly the ones the five topologies later depend on. It is ready to be *converted*, and the conversion is real work — expect ~8–12 SPECs, and expect the SPECs to push back on the PRD (drop templ, raise/restate the memory budget, delete `[stats]` from the artifact, redefine shadow mode, split the MVP).

**BUILD WITH CHANGES** — (1) v0.1 vertical slice with the deferred list frozen; (2) SPEC-DATA (ledger schema, ids, sig version, single-writer, durability window, retention, scrubbing, state root) written and reviewed **as a precondition to any code**; (3) verification redefined as liveness-backed, not absence-based; (4) skill/play artifacts immutable + signed + staged, stats moved out of the artifact; (5) ops guardrails (config precedence, version stamping, port-collision check, state root, self-watchdog).
